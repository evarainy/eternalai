## 4. Runner 必须断言的内容（spec verbatim，逐条覆盖）

每个 GT fixture 的断言点（spec §12.2 / §12.8 acceptance）：

1. `then_response.status`（completed / blocked / waiting_user / failed / no_capability_found）。
2. `then_response.envelope.message_contains[]`（子串全部命中）。
3. `then_response.envelope.ui.component_type` / `ui.action` / `ui.target_system`（fixture 里是带点的扁平 key，如 `"ui.component_type"`、`"data.workflows.length"`——按字面 key 读）。
4. `then_response` 涉及的 `error_code`（负向 / 注入路径）。
5. `then_trace.event_sequence`：实际 trace 事件序列必须**包含** fixture 列出的事件（顺序敏感；fixture 可多不可少 must-have）。
6. **短路终态 Trace 事件矩阵**（spec §12.4.1，verbatim 见下）：按终态校验 must-have / must-not-have；**must-not-have 事件一旦出现即判该 GT failed**。
7. `then_forbidden[]`：禁止项必须**检查值模式，不只检查字段名**（spec failure `forbidden_trace_token`）——
   `trace_contains_token`（Trace/Response/Log 不得出现 token / cookie / sessionid / Bearer）、
   `response_contains_internal_url`、`mock_*_was_called` / `mock_adapter_was_called`（对应 adapter spy 调用计数=0）、
   `fallback_to_first_binding` / `fallback_to_system_scope` / `response_data_not_null` 等。
8. `adapter_assertion.must_be_called` / `must_not_be_called`：以 runner 自建 **spy 调用计数**断言（must_not_be_called=true 但计数 >0 → failed）。

## 5. Machine-readable summary + 状态语义（spec §12.8 acceptance）

`scripts/run_golden_tasks.py` 输出每个 GT 的状态及合计。**状态语义严格定义（防止用 skipped/not_applicable 掩盖实现失败）**：

- `passed`：所有断言（response + trace + 短路矩阵 + forbidden + adapter_assertion）全部满足。
- `failed`：**任一断言不满足即 failed**——包括 Runtime skeleton 未产出 fixture 期望的 trace 事件、response 不符、forbidden 命中、adapter 调用计数不符。**Runtime 能执行但结果不达标 = failed，不是 skipped。**
- `skipped`：**仅限测试前置条件根本无法执行**（如缺少运行所需的外部资源），且必须带 reason；**不得用于"Runtime 没实现某事件"**——那是 failed。
- `not_applicable`：仅用于该 GT 在本阶段确不适用，必须带 Task Record schema 的完整字段（`not_applicable_reason` / `not_applicable_scope`(current_phase_only | waiting_dependency | intentionally_deferred) / `blocked_by_task_id` / `activation_task_id` / `expiry_condition`）；**不得掩盖实现失败**。

建议 JSON：

```json
{
  "total": 11,
  "passed": 0, "failed": 0, "skipped": 0, "not_applicable": 0,
  "results": [{"golden_task_id": "GT-001", "status": "passed|failed|skipped|not_applicable", "reasons": ["..."]}]
}
```

**禁止把 failed 用例改成恒真断言（spec failure `test_rewrite_detected`）。**

## 6. CI 激活 — 🔴 blocking 红线 + 人工决策（不是可选的 partial-done）

spec §12.8（行 3675-3681）+ §13（行 4753）硬要求：“P0-GT-002 必须证明 Golden Task CI 检查已从 not_applicable 激活，**不能只实现 runner 脚本**”。

**实际 `.github/workflows/ci.yml` 中没有任何 golden / not_applicable 占位**（grep 零命中，属 INFRA-007 实现偏差）。所以无法“激活”一个不存在的占位。两条路径都触及红线 / 需人工决策：

- 路径 1：在 `ci.yml` **新增** Golden Task runner 的 CI step（调用 `scripts/run_golden_tasks.py`）。→ **修改 `.github/workflows/ci.yml` = CI/CD 配置变更 = 红线**，必须人工批准后才能改。
- 路径 2：提交 **task patch / ADR**，澄清 INFRA-007 未放 not_applicable 占位的偏差，并重新界定 CI 激活方式 / 责任边界。

**这是 blocking gate，不是可接受的 partial-done：**
- runner + assertions + script + 两个 meta-test 全部完成、本地 `uv run pytest tests/golden_tasks/` 通过后，到 CI 激活步骤 **STOP-AND-ASK 人工选择路径 1 / 路径 2**，**不得自行修改 `.github/workflows/ci.yml`**。
- **在 CI 激活闭环（路径 1 经批准并落地 + active 断言通过，或路径 2 的 patch 被接受）之前，Task Record 状态记 `blocked` / `NEEDS_HUMAN_DECISION`，不得记 `passed`。** runner 机制完成只是必要条件，不是本任务的完成条件。

## 13. Constraints to Carry Forward

- 不写 `__init__.py`（namespace package）；不引入 `pytest-asyncio`，用 `asyncio.run()` 跑 `RuntimeImpl.handle_user_message`。
- runner 是裁判：fixture / Runtime 实现的差距 → 断言不满足 = **failed**（§5），绝不改 fixture、不改实现、不恒真断言、不用 skipped/not_applicable 掩盖。
- `adapter_assertion` 靠 runner 自建 spy 计数（adapter 无内置 call count）；显式调用 conftest 的 `apply_mock_state`。
