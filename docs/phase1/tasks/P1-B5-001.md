## 目标（done_when）

1. 同一 tenant/session/ai_user 的后续消息可使用此前成功轮次的结构化摘要，
   不保存或注入原始对话全文。
2. 不同 session 与相同 session 下不同 ai_user 的记忆互不可见，并由独立 pytest
   参数实例锁死。
3. 隔离键结构为 `(tenant_id, session_id, ai_user_id)`；当前 tenant 仍为
   `default`，不声称端到端跨 tenant 已验证。
4. 每个 context 最近 5 条、最多 32 个 context，总上限 160 条；两层淘汰均可精确断言。
5. 记忆只含 `capability_id` 与 `terminal_status=completed`；message、arguments、
   Gateway data、完整业务载荷及凭证值不得进入记忆或下一轮 context。
6. denied、failed、waiting_user 与 no_capability_found 不写入成功记忆；既有
   Runtime/Policy/Identity/Gateway/Workflow 行为不变。

## 存储与 tenant 决策

选择具体 `SessionMemory` 组件并由 composition 注入 Runtime，而不扩
`SessionStorePort` / `SessionRecord`。本任务明确排除 DB、跨进程与跨天持久化；
扩持久化契约会产生本任务无法兑现的持久化承诺。组件生命周期等同单个
`RuntimeImpl` 实例，无全局单例，进程重启后丢失。

当前入口没有可信 tenant 参数，因此仍显式使用 `default`。本任务只验证三元键的
结构隔离；端到端跨 tenant 隔离是保留风险。只有上游可信 tenant 身份进入 Runtime
后，才能补真实跨 tenant 主链测试并宣称该维度已验证。

## 敏感值过滤

Runtime 仅在最终 completed 后向 Memory 传入 capability_id；原消息、参数、输出和
业务载荷从不进入 Memory API。Memory 再拒绝 Bearer 及 credential assignment 形态，
覆盖 authorization、sessionid、access/refresh token、cookie、password/passwd、
API key、secret/client secret/private key。
