## 2026-07-27 — P2-PILOT-FOUNDATION-001 `uvicorn` runtime dependency

`2026-07-27` 雨爷批准 `P2-PILOT-FOUNDATION-001` 新增运行时依赖 `uvicorn`，范围仅限 ASGI server 进程启动，不含部署编排。依赖白名单登记于 `docs/dev/dependency_policy.md` 的 Dependency Allowlist。

## 2026-08-03 — 决定一：写操作凭证与问责

写操作使用用户自己的 OA 凭证执行，OA 审批记录上是用户本人；每次写操作必须人工确认，AI 拟好、用户点确认才执行，确认动作本身留痕；与 `P2-CONFIRM-RESUME-001` 方向一致。

## 2026-08-03 — 决定二：数据库访问边界

数据库不算“目标系统”：不进外部系统名册、不做 IdentityMapping、不加 `db` 枚举值，因此不需要 schema 变更；但 AI 对数据库的每次访问必须在 Trace 里可查。

## 2026-08-03 / 2026-08-12 修订 — 决定三：企业级密钥

企业级密钥的责任人为运维；纯内网不设定期轮换；通过配置文件手工更新，不建设运行时管理页面。

## 2026-08-03 — 决定四：Golden 策略（逐字）

负向、边界和安全拒绝用例的题面、预期、禁止项、分类及判卷契约冻结，修改需雨爷明确批准。所有既有正向题面同样不可原地改写，只能新增后继题并在题外生命周期清单中停止旧题运行。判卷契约或运行选择规则变更时，必须按同一版本包全量回放并明确披露影响。每修复一个真实缺陷，必须新增一条能在未修代码上失败、修复后通过、且走原缺陷路径的永久回归证据；缺陷属于 Golden Runtime 观察边界时才新增 Golden Task，否则放在最小且忠实的单元/集成/API/浏览器层。

## 2026-08-17 — 蓝图原则修订：企业控制内核自有，通用执行内核复用

**决定**：蓝图 L2435「任何第三方框架都不能替代 Agent Runtime」修订为「企业控制内核（Gateway / Policy / Identity / Secret / Trace / Evidence）必须自有；通用执行内核（agent loop、上下文工程、持久 checkpoint、沙箱、子 Agent）优先复用成熟组件并保持可替换」；蓝图是冻结文件，落地方式是发 ADR 覆盖 L2435 / L2613，不编辑蓝图本体，具体框架选型仍未定。

**为什么**：实盘核对过——我们已建成的那些层第三方框架都不提供，而框架真正强的那些层我们完全空白，两边几乎不重叠，所以问题从来不是「要不要换掉自研」，而是「要不要补一层从没建过的」；同时 2026 年候选框架换代极快（一次一手核对里，三天内五个候选有三个变了版本语义），把执行底座冻进架构最深一层，等于把最大的不确定性锁死。

**影响面**：所有涉及多轮循环、缺参追问、规划、上下文工程、持久 checkpoint、子 Agent / 沙箱的后续任务；`AgentOrchestrationPort` / `WorkflowEnginePort` 接缝棒（欠债已登记在 `PHASE2_PLAN.md`）；此后任何「要不要引入某框架」的讨论以本条为起点，不再重开「自研 vs 复用」的原则辩论，只辩选型与时机。

## 2026-08-17 — 蓝图优化的落地顺序（四步走）

**决定**：按 `修文档漂移 → 内网真实 smoke → 修工具描述（能力模型可见面收紧）→ 留孔 + 装现成组件` 四步推进；前两步已完成（`P2-GOV-SYNC-011`；2026-08-13 内网 `smoke.ps1 verify` 全绿），当前落在第三步；「留孔」指补 `AgentOrchestrationPort` / `WorkflowEnginePort` 生产接缝，蓝图 L2373 / L2402 / L2403 早已写下这两个名字，只是代码里从未落地。

**为什么**：装第三方执行内核之前必须先有接缝，否则框架类型会长进业务代码——框架下次改 API 时改的是业务逻辑，想换第二家的成本比第一次更高；第三步是第四步的前置，两件必须按序，不能对调。

**影响面**：DAG 排序权归 GOV-SYNC，实现棒不得自行挑后继——本条即是已裁定的顺序，可直接机械传播；「装现成组件」不早于第三步收口，任何提前引入框架的提案先回到本条；补接缝本身是把蓝图欠的账补上，不是新增架构，因此不构成新的架构停点。

## 2026-08-17 — DeepSeek Harness：不引入运行时插件容器

**决定**：不采纳 DeepSeek Harness / Cordis 式的运行时插件容器（动态加载第三方代码、HMR 热插拔、同进程无隔离、显式宣称「没有 privileged core」）；其能力契约层与我们 `app/ports/` 属同构设计，不需要为它重构；可借鉴的只有两条——`Model-visible means logged`（进入模型请求的一切必须能从持久日志完整重建）与「能力的模型可见面只走单一 allowlist 投影」。

**为什么**：「没有 privileged core」与不可协商不变量「任何执行必须经 Gateway → Policy → Adapter → Evaluator → Trace 且不可绕过」正面冲突；运行时加载第三方代码会让制品不可复现、供应链审查失效；其 `inject` 的真实语义只是「等该服务就绪再加载」，不是权限模型；其可短路的 `waterfall` 事件链若承载强制通路，任一监听器不调用 `next()` 就能把 Policy / Evaluator / Trace 全绕过。

**影响面**：其他窗口不必重开「是否插件化」的调研；第四步「装现成组件」的候选范围排除运行时插件容器类方案；可借鉴的第二条与第三步「修工具描述」是同一个面（见 `docs/adr/phase2/ADR-P2-CAPABILITY-INJECTION-001-planner-contract-narrowing.md` 与 `PHASE2_PLAN.md` 能力注入欠债），并入该棒执行；第一条需先核实现有 Trace 是否已记录完整 LLM 输入，未核实前不排期。

## 2026-08-18 — 产品定位：AI 工作操作系统与三种工作表面

**决定**：EternalAI 不定义为聊天机器人、智能工作台、业务中台或企业 IM，而定义为部署在现有业务系统之上的 **AI 工作操作系统**。系统持续接收 IM、OA、文件、业务系统事件和人工输入，将其转化为可治理的工作对象，经 AI Runtime、Capability、Workflow 与 Skill 受控执行，再把同一工作状态投射到三种互补的工作表面：

- **通信空间 / IM（人与人）**：承载沟通、文件、通知，也是最重要的工作事件来源之一；
- **AI 共事界面（人与 AI）**：承载通用问题、开放任务、自然语言指令、连续协作与结果修订；
- **工作台（人与工作）**：承载责任、状态、时限、流程、阻塞、证据、确认和交接。

三者不是三个数据孤岛：IM 中的消息可以形成待办候选，AI 对话可以创建或继续处理工作，工作台结果可以返回原会话，工作对象可以追溯来源消息；身份、上下文引用、工作状态和审计记录必须贯通。原始消息仍以 IM 为权威来源，正式业务状态仍以 OA 等源系统为权威，EternalAI 的 Work Object 只作为跨系统工作编排状态的权威对象，不复制成第二套业务真相。

**覆盖关系**：本决定覆盖 `_scratch/ADR_前端体验架构_草案.md` 中「工作队列为主体」的产品级定位；工作队列仍是工作台的重要组成，但不再代表整个产品。该草案关于常驻 AI 入口、按结果寿命决定落位、复杂事项进入工作室、受控组件组合和 SDUI 与前端框架隔离的决定继续有效。

## 2026-08-18 — 聊天事件候选闸门：AI 止于候选，执行责任归人

**决定**：在「AI 读取聊天内容并识别潜在工作」这条路径中，AI 的自动权限永远止于 **Work Candidate / 待办候选**，固定链路为：

```text
聊天消息 / 引用消息
  → AI 提取事实、责任人、时限、来源和歧义
  → 生成待办候选卡片并推入工作台
  → 人工审阅、补充或驳回
  → 人工明确确认后转为正式 Work Object 并进入流程
  → 任何外部执行仍经 Gateway → Policy → Adapter → Evaluator → Trace
```

AI 不得仅凭聊天语义把候选升级为正式工作，不得把领导发言、群主身份、`@某人`、表情、已读状态或「好的/收到」等自由文本推定为执行授权。由聊天产生的候选升级、流程启动和任何外部写操作，都必须绑定一次明确的人机交互确认；Trace 至少记录确认人、确认时间、候选版本、来源消息引用、补充字段、确认结果和后续 Work Object。责任归属于作出确认的人，AI 负责建议、准备和留痕，不承担法定或管理责任。

一条消息可以产生多个候选，多条消息也可以汇聚为一个候选；不得强制建立 `message = task` 的一一映射。原始聊天内容不得直接灌入全局知识库或无边界 RAG，只能在显式触发和 Policy 允许的范围内读取当前消息、引用链及必要的有限上下文。

## 2026-08-18 — 聊天只做卡片路由，不承载自由文本执行

**决定**：人与人仍可在 IM 中自由交流，但 **AI 在聊天侧的工作交互只使用结构化卡片和受控按钮，不接受自由文本作为直接执行指令**。聊天借鉴审批卡片的交互方式，但只负责发现、通知和路由，不承载正式业务执行。

聊天卡片只允许执行以下类型的动作：

- 查看来源、查看依据或查看当前状态；
- 接受候选、驳回候选或标记稍后处理；
- 打开工作台中的结构化表单、事项工作室或确认页面；
- 对已经存在的工作对象进行签收、订阅或跳转。

卡片按钮不得直接调用业务 Adapter 或绕过工作台确认。候选卡片上的「进入办理」只表示接受候选并打开结构化页面；用户在工作台核对范围、字段、目标系统、风险和预期副作用后，再点击「确认执行 / 提交」才构成执行授权。「驳回候选」只改变候选状态，不等价于对源业务事项作正式驳回。

卡片动作使用稳定的 `action_id`、对象引用、版本号和幂等键，由 Surface Adapter 转换为统一 UserAction；不得把 Tool 名、任意 URL 或可执行参数直接塞进聊天消息。

## 2026-08-18 — 工作台向聊天反向推送：把注意力逻辑带回沟通现场

**决定**：工作台不仅接收聊天产生的候选，也应根据与「今日工作概览」相同的优先级逻辑，主动向适当的 IM 会话推送结构化提醒卡片，形成 `沟通 → 工作 → 执行 → 结果 → 沟通` 的闭环。典型触发包括即将超时、已经逾期、等待本人确认、AI 已准备完成、权限或数据受阻、需要交接和正式升级。

推送卡片只展示最小必要摘要、紧迫程度、责任归属和下一动作，并提供「去处理 / 查看详情」等路由按钮；不得在聊天中直接完成业务执行。推送必须引用唯一 Work Object，复用工作台的优先级、去重和状态计算，状态变化时更新原卡片而不是重复刷屏。

利用沟通环境的可见性形成责任提醒，但不得演变为模型自行决定的公开点名或排名：默认私发责任人；只有制度配置、原事项所在群或正式逐级升级规则允许时，才推送到群聊或负责人。接收范围、升级路径、频率限制、静默/班次策略、已读签收和每次推送都必须可配置、可审计。

## 2026-08-18 — Ant Design 6 卡片复用与多 Surface 渲染

**决定**：Web 阶段以 Ant Design 6 作为统一组件底座，同一份工作卡片语义与状态在 IM、工作台和事项工作室中复用，但按 Surface 采用不同密度：聊天使用紧凑卡片，工作台使用摘要卡片，事项工作室使用完整详情。复用的是 **语义协议、状态、动作合同和 Ant Design 6 组件实现**，不是强迫所有界面显示完全相同的布局。

协议继续保持语言和框架中立：权威源位于自有 SDUI / Work Card Schema，Ant Design 6 只存在于 Web Renderer。JuggleIM 消息载荷只携带卡片协议版本、对象引用和允许的动作，由 EternalAI Web Renderer 渲染；不得让通信产品的数据结构反向成为工作对象或卡片协议的权威定义。这样既能在当前 Web 产品中复用 Ant Design 6 卡片，也保留未来原生客户端新增 Renderer 的空间。

## 2026-08-18 — 插槽式模块边界：可替换，但不引入无特权核心的插件容器

**决定**：产品模块采用插槽式组合，借鉴 DeepSeek Harness 在模块装配、替换和维护方面的思路，但不采纳其动态加载任意第三方代码、HMR 热插拔、同进程无隔离或「没有 privileged core」的运行时插件模型。当前阶段的插槽由稳定契约、静态注册表和 allowlist 控制，在构建或部署时装配，经审查后才能进入产品。

优先预留的插槽包括：

- Communication Event Source / Delivery / Admin Adapter；
- Work Projection、首页优先级与角色视图；
- Card Renderer 与 Surface Variant；
- AI 共事面板、事项工作室辅助面板；
- Skill / App 入口与受控动作目录。

插槽解决「模块可以替换、独立维护、按需装配」，不改变企业控制内核的唯一性。任何插槽模块都不得绕过 Identity、Policy、Gateway、Evaluator、Trace 和 Evidence，不得自行扩大消息读取范围、发明新动作或直接执行目标系统操作；契约测试、架构边界测试和负向权限测试必须随模块实现一并提供。

**与 2026-08-17 DeepSeek Harness 决定的关系**：上一决定继续有效；本条只是确认可以借鉴其插槽化和可替换性，不恢复已经否决的运行时插件容器。

## 2026-08-18 — 当前前端与通信技术路线

**决定**：当前按方案 A 推进：EternalAI 保持自有 Ant Design 6 Web 外壳，以 JuggleIM 作为首个通信内核验证对象，通过自有 Communication Adapter 接入；工作对象、身份、权限、Policy、卡片协议和执行链均归 EternalAI。现阶段只做 Web，不开发桌面或移动原生客户端，也不再进行无目的 IM 选型调研。

重新打开通信产品选型的触发条件仅限：JuggleIM 验证出现硬性缺口；进入正式客户端开发里程碑；出现跨单位联邦通信、高安全加密等新增要求；或届时市场出现明显更合适的新产品。冻结蓝图本体不直接修改；本组决定作为后继决定生效，并在下一版蓝图中吸收。任何早期文档若允许「聊天自由文本直接驱动 Tool」「AI 自动把候选升级为正式任务」「聊天卡片按钮直接执行目标系统操作」或把工作队列等同于整个产品，均以本组 2026-08-18 决定为准。

## 2026-08-18 — 卡片动作的授权边界：引用不传递权限

**决定**：任何 Surface（IM、工作台、AI 共事界面、事项工作室）上的卡片动作，**授权依据只能是服务端签发、绑定到 `(tenant, principal, work_object, card_version)` 的不透明引用**。转发、引用、复制、截图重放消息或链接**不传递操作权**；服务端对每一次动作重新解析该引用并按当前 Principal 与 Policy 重新授权，主体失配一律拒绝并留痕。明文业务 ID（`task_id`、`work_object_id` 等）可用于展示、关联和日志，**不得作为授权依据**。

**为什么**：卡片进入 IM 后暴露出 Web 内没有的攻击面——消息可被转发、引用、搜索和截图，「卡片出现在你的会话里」不等于「你有权执行它」。若授权只依赖稳定 `action_id` 加明文对象引用，甲把候选卡片转给乙、乙点「接受候选」即可越权。该风险不限于 IM：工作台与共事界面的卡片引用同样会被复制粘贴，因此本条对所有 Surface 生效。

**影响面**：卡片协议与 `UserAction` 合同、Surface Adapter、JuggleIM 消息载荷字段、Trace 的拒绝留痕、后续所有 Renderer 实现；与 2026-08-18「聊天只做卡片路由」中的 `action_id`/对象引用/版本号/幂等键为同一套字段，本条规定其中「对象引用」必须是不透明且绑定主体的。

## 2026-08-18 — 本地 capability provider 的边界澄清

**决定**：「现阶段只做 Web，不开发桌面或移动原生客户端」**不排除本地 capability provider**。该 provider 不带浏览器内核、不带 UI、不是原生客户端，只是装在终端上、经 `localhost` 被 Web 应用调用的瘦服务，用于浏览器做不到的能力：Office COM、扫描仪、Win32 老软件、后台长驻任务。它与通信内核选型互不影响，予以保留。

**为什么**：桌面壳被否是因为 Electron / Tauri 在 Win7 与麒麟上只能冻结在已 EOL 的浏览器内核（依据见 `_scratch/查证_桌面壳与FileSystemAccess_20260818.md`）；本地 provider 不含内核，不受该约束。若不写明，「不开发客户端」会被读成连本地 provider 也一并排除，导致上述四项能力无处落地。

**影响面**：Excel 与本地文件场景的能力上限、终端分发方式、`Local Capability Provider` 相关的插槽与接缝；Excel 报表主流程仍以纯 Web（File System Access）为默认路径，本地 provider 只承接浏览器确实做不到的部分。

## 2026-08-18 — 通信内核的当前定性：初步筛查，未定选型

**决定**：JuggleIM 目前只是**架构完善所做的初步筛查对象**，不构成已定选型。当前阶段先把 Web 做出来、把流程跑通；IM 相关工作排在 Web 与工作流基本成型之后，**届时重新做选型决定**。现在不为 JuggleIM 编写验证清单、不做 IM 选型调研、不将其写入任何实现棒的前置。

**为什么**：2026-08-18「当前前端与通信技术路线」中「以 JuggleIM 作为首个通信内核验证对象」易被读成既定选型；实际用意是为整体架构预留通信层位置，验证时机在后。提前投入验证或实现属超前工程。

## 2026-08-18 — DeepSeek Harness 评估结项：经验证不适合，不再重开

**决定**：DeepSeek Harness（含 Cordis 插件模型）**经验证不适合本项目，评估到此结项**。相关调研材料与内网副本可清理，本条即为永久记录；此后不再重开该候选，除非出现推翻下列任一理由的新证据。

**不适合的理由（逐条，均经查证而非推测）**：

1. **架构冲突**：它显式宣称「没有 privileged core」，与本项目不可协商的「任何执行必须经 Gateway → Policy → Adapter → Evaluator → Trace 且不可绕过」正面冲突。
2. **强制通路可被短路**：其 `waterfall` 事件链中任一监听器不调用 `next()` 即可把 Policy / Evaluator / Trace 全部绕过；若把强制通路架在这条链上，绕过是一行代码的事。
3. **`inject` 不是权限模型**：其真实语义只是「等该服务就绪再加载」，不承载任何隔离或授权语义，不能拿来当能力边界。
4. **供应链不可审查**：运行时动态加载第三方代码 + HMR 热插拔，导致制品不可复现、离线交付与供应链审查同时失效——这在内网无镜像、依赖必须整体拷入的部署条件下不可接受。
5. **平台不匹配**：其 Node 引擎要求为 `^22.19.0 || >=24.0.0`，而 Windows 7 的 Node 支持终止于 13.x（2020-06-01 EOL）；作为客户端底座在目标平台上直接不可用。
6. **无重构收益**：其能力契约层与本项目 `app/ports/` 属同构设计，改用它并不能省掉已建成的层，只是换一套等价抽象。

**保留可借鉴的两条**（与否决不矛盾，已并入其他棒）：`Model-visible means logged`——进入模型请求的一切必须能从持久日志完整重建；以及「能力的模型可见面只走单一 allowlist 投影」，并入能力注入面收紧棒（见 `docs/adr/phase2/ADR-P2-CAPABILITY-INJECTION-001-planner-contract-narrowing.md`）。模块装配与可替换性的思路已由 2026-08-18「插槽式模块边界」条独立承载，不依赖该框架。

**影响面**：2026-08-17「不引入运行时插件容器」条继续有效，本条是其结项记录与理由固化；`_scratch/` 下以 DeepSeek Harness 为骨架的架构说明书 v0.1 / v0.2 已停止修订并被 2026-08-18 决定组取代；四步走第四步「装现成组件」的候选范围排除运行时插件容器类方案。

## 2026-08-18 — 「候选」正名：`WorkCandidate` 与 `SkillCandidate` 不得简称

**决定**：仓库中**禁止单独使用「候选」/`Candidate` 指代具体对象**，必须写全称：

| 全称 | 指什么 | 状态机 | 出处 |
|---|---|---|---|
| `WorkCandidate` / 待办候选 | AI 从聊天、OA、文件或业务事件中提取出的**工作候选** | 提取 → 人工审阅/补充/驳回 → 人工明确确认 → 转正式 Work Object | 2026-08-18「聊天事件候选闸门」 |
| `SkillCandidate` / Skill 候选 | 可登记、审查、拒绝，且**不能自动发布或执行**的 Skill 提案 | 登记 → 审查 → 接受/拒绝 | `P2-SKILL-CANDIDATE-001` |

适用面：类名、字段名、表名、API 路径、枚举值、Trace 事件名、错误码、测试名、文档标题与正文一律用全称。已有的 `P2-SKILL-CANDIDATE-001` 这一 `task_id` 保持不变（task_id 是历史路标，不改写），但该棒产出的所有代码标识符与文档表述须用 `SkillCandidate`。

**为什么**：两者的状态机形状几乎一样（登记/提取 → 审查 → 接受或拒绝），但对象、责任人、权限面和风险等级完全不同——`WorkCandidate` 被误升级会导致未经授权的业务执行，`SkillCandidate` 被误发布会导致未审查的能力进入运行时。一旦代码里出现 `CandidateStore`、`candidate_id`、`approve_candidate` 这类名字，读代码的人无法判断动的是哪一种，而这恰好是最不该猜的地方。命名歧义在这两个对象上会直接变成安全缺陷。

**影响面**：`P2-SKILL-CANDIDATE-001` 开工前须按本条确定标识符；`WorkCandidate` 相关的协议、卡片类型与存储在 IM/工作台棒中按本条命名；后续如出现第三类候选，同样必须带限定词，不得复用裸「候选」。

## 2026-08-19 — 裁决：Work Object 首棒走 OA 直通，`WorkCandidate` 留位不实现

**决定**：Work Object 层按「最小真实纵切」建设，但**首个来源不经 `WorkCandidate`**。两条来源链路的形状固定为：

| 来源 | 链路 | 人工确认的作用 |
|---|---|---|
| OA 待办等**结构化、在源系统中已成立的正式事项** | 直接生成 Work Object，**不经 `WorkCandidate`** | 不确认「是不是工作」；确认只发生在要写回目标系统之前 |
| IM / 邮件等**非结构化、由 AI 提取**的内容 | `WorkCandidate` → 人工审阅补充或驳回 → 人工确认 → Work Object | 判断真伪、补全字段、承担责任 |

首棒只实现第一条链路，第二条链路**留出位置但不实现**。`TaskRecord` 保持「一次执行记录」语义不变，Work Object 只按 ID 引用它，不改造、不合并。Work Object 首版保持小聚合：来源引用、责任人、时限、当前状态、确认记录；聊天、执行历史、附件、审批、部门视图只存 ID 或投影，不塞进同一对象。

**为什么**：`WorkCandidate` 的设计意图是「AI 从非结构化内容里提取出可能的工作，由人把关」（2026-08-18「聊天事件候选闸门」）。OA 待办在 OA 里已经是白纸黑字的正式流程，不存在「是不是工作」的疑问。用它做首个候选，人工确认会退化成「我知道了」的已读回执，而首版定下的语义会被用户学走；等真正接入 IM、AI 开始从聊天里提取时，才会发现确认本该承担判断真伪与补全信息的职责，那时要改的不只是代码，还有已积累的历史确认记录——那些记录里的「确认」是什么含义将说不清。

外部实践支持这一区分但**不构成行业铁律**：Microsoft Planner → To Do 让已分配的 Planner 任务直接出现在 To Do，两处是同一份对象；Jira 从 Asana / monday / Trello 导入的 work 直接落为 work item；而 monday.com AI Notetaker、ServiceNow Now Assist、Jira Rovo 对 AI 生成的内容都先给候选、用户选择后才创建。反例同样存在：Asana AI Teammates 可直接创建正式 task，其额外审批卡在权限与责任变更上而非「这是不是任务」。因此本条是有据的设计判断，不是照搬共识。

**影响面**：Work Object 首棒的 Scope 与验收；`WorkCandidate` 相关的协议、卡片类型与存储推迟到 IM 或其他非结构化来源接入时，届时按 2026-08-18「聊天事件候选闸门」实现；本条不改变该决定对 AI 自动权限止于 `WorkCandidate` 的约束，只明确它的适用面是非结构化提取路径。**开工前置未解除**：Work Object 与 OA 的状态同步策略尚未裁决（见 `PHASE2_PLAN.md` 欠债表），该策略决定 Work Object 有哪些字段，必须先定。

## 2026-08-19 — 裁决：不为已成立的正式事项设「确认它是不是工作」这一步

**决定**：任何 Surface 上都**不得**为「在源系统中已经成立的正式事项」增加一次只用于确认其存在或性质的人工步骤。人工确认只在满足以下任一条件时设置：授权一次会改变外部系统状态的执行、补全系统无法自行获得的信息、变更责任归属或访问权限、或裁决 AI 在不确定情况下的提取结果。

判据：**如果绝大多数情况下用户只会选同一个答案，这个确认就应当删掉。**

**为什么**：这不是体验问题，是安全问题。微软的确认对话框规范给出可操作判据——必须存在明确且合理的「不继续」理由，且用户有时确实会选择不继续；约 98% 场景都选同一答案时应移除确认。更关键的是习惯化的外溢效应：MIS Quarterly 的五日纵向实验与三周现场实验测到，重复暴露后用户对警告的注意力与遵从度显著下降；USENIX SOUPS 的后续研究进一步发现，**频繁的普通通知会把这种习惯化泛化到关键安全警告上**，不是只对那一个弹窗麻木。

本项目整条链路的最后一道人工门是 `confirm_card`——低风险写入前的执行授权。若工作台先用大量无意义确认把用户训练成机械点击，那道真正的门会跟着失效。NIST AI RMF 与欧盟 AI Act 第 14 条同样把人工监督强度绑定到风险、自治程度与使用语境，而不是一刀切逐条确认。

**影响面**：工作台、IM 卡片与 AI 共事界面的所有确认点设计；`P2-LOW-RISK-WRITE-001` 的 `confirm_card` 价值保全；任何后续「要不要加一次确认」的提案先回到本条判据。本条不放松 2026-08-18「聊天事件候选闸门」——那条约束的是 AI 从聊天提取的路径，其确认恰好满足本条「裁决 AI 不确定提取结果」的条件。

## 2026-08-19 — 裁决：两个执行内核接缝从现有实现提取，不等第三方框架

**决定**：`WorkflowEnginePort` 与 `AgentOrchestrationPort` 两个接缝**现在就建，第一个实现是包住项目自己已有的代码**，不等第三方框架到位：

- `WorkflowEnginePort` 包住现有 `WorkflowEngine` 的 `execute` / `resume`，让 `RuntimeImpl` 不再直接依赖具体类；
- `AgentOrchestrationPort` 包住 `RuntimeImpl` 已经在做的编排行为（能力选择、执行协调、响应组织）。

两个端口必须分别说明自己承载的职责，不得互为别名：`WorkflowEnginePort` 只表达可持久恢复的流程执行；`AgentOrchestrationPort` 只表达代理循环、委派与工具候选编排。端口签名只表达本项目需要的输入、结果、取消/恢复与错误，**不得出现任何候选框架的类型**（LangGraph、Temporal、OpenAI Agents SDK、Microsoft Agent Framework 等的 checkpointer、`RunState`、thread ID、task token 一律留在 adapter 内）。

**为什么**：此前的分歧是「建空接口」与「等第一个框架一起落地」。两者都不对——空接口是在猜未来框架要什么；而孔与组件同时到，「先留孔」的保护就没有了：设计接口时手边摆着那个框架，很难不照着它的形状画，这正是 2026-08-17「四步走」要防的「框架类型长进业务代码」。

第三条路有明确的工程依据。Branch by Abstraction（Fowler 原文与 AWS Prescriptive Guidance 的六步法一致）的顺序就是：抽象层先捕获**现有**调用方与**现有**实现之间的交互 → 现有调用全部改走抽象 → 新实现再对接同一抽象 → 渐进切换。Extract Interface 的触发条件同样是「已有客户端在用同一子集」，不是预留未来。Go 官方工程规范直接写明：接口被使用之前不要定义它。YAGNI 明确覆盖「为未来灵活性预留抽象」这一动机。

`RuntimeImpl` 中的编排行为是**现存的真实实现**，因此从它提取接口既不是空抽象，又让接缝先于框架存在，同时满足两个约束。

**影响面**：四步走第三步「留孔」的具体形状；`app/ports/` 新增两个 Protocol 属 A 档，需独占 worktree、监理窗口与 Opus 桥；第四步「装现成组件」时第三方只是第二个实现，不改端口。风险提示：Sandi Metz 的 The Wrong Abstraction 指出错误抽象比重复代码更昂贵——若第二实现出现时发现端口形状不合，应撤回抽象重做，而不是加参数和条件分支维持它。

## 2026-08-19 — 裁决：`HumanGatePort` 独立，`CredentialBindingPort` 不新建

**决定**：不新增 `CredentialBindingPort`；凭证绑定的现役承载记录为 `IdentityMappingPort` 与 `app/ports/auth.py` 中的凭证存取契约，这是相对冻结蓝图 §11.2 端口清单的**既定偏差**，理由记录于本条。

新增 `HumanGatePort`，承载「谁对哪一个不可变请求作了什么决定」。确认请求必须由服务端生成并持久化，绑定主体、动作摘要或 digest、版本集合、有效期与唯一请求 ID；只接受确认或驳回；**动作内容一旦变化，旧确认立即失效并新建请求**。

**为什么**：凭证绑定解决「系统以谁的身份访问目标系统」，人工确认解决「谁同意了哪项具体动作」，是两个不同问题，现有两个端口已分别覆盖前者的映射与凭证替换点，再建一个只会制造第三处真相。而人工确认目前没有独立承载——语义散在 `policy_guard` 的 `confirm` 决策值与 `response_envelope` 的 `ConfirmCard` 中，既无法持久化「谁确认了什么」，也无法在内容变化时使旧确认失效。

OWASP Transaction Authorization 的 What You See Is What You Sign 要求用户确认显著交易数据、授权在服务端强制执行、验证数据由服务端生成并保存，且交易数据在确认后变化时应让旧授权失效并重启流程。本条按该要求落形状。

**影响面**：`app/ports/` 新增 `HumanGatePort` 属 A 档；与下条版本绑定是同一条安全链的两面，**合同必须一起设计**；Work Object 首棒的写回确认是它的第一个真实消费者。

## 2026-08-19 — 裁决：版本绑定推广既有 Workflow 锁定模式，并前置低风险写入

**决定**：建立一次 Task 从启动到确认、恢复、执行都不变的版本绑定清单，并把它列为 `P2-LOW-RISK-WRITE-001` 的**硬前置**。

**影响面**：`P2-LOW-RISK-WRITE-001` 的 `depends_on` 新增版本绑定棒；与 `HumanGatePort` 合同一起设计；工作量按「推广既有模式」估算，低于从零建。

**为什么**：第 3 条是相对此前建议的修正。当前 Admin API 只接受资源筛选字段，不接受 page / cursor / page size / sort 参数，返回结构只有 `items`，后端 Task Store 使用固定上限并按 task ID 排序——因此「先用现有 Admin 页证明分页排序可复用」在不扩后端合同的前提下无法完成，若只在浏览器里切数组分页，等于用本地假象冒充服务端能力。而 Work Object 首版数量必然很小，提前定分页合同是在没有真实压力时猜。TanStack Query 官方建议用资源级 `queryOptions` 共享 query key 与 query function，query key 只包含真正改变结果的变量；这套做法在第二个真实列表出现时再抽取，成本更低且不会长歪。

第 1、2 条依据 AWS 与 Microsoft 的 ADR 指南：已接受的决定保持不可变，方向变化时用新记录 supersede 旧记录，不回改历史。

**影响面**：`PHASE2_PLAN.md` 的 DAG 表与主链描述；`P2-SKILL-CANDIDATE-001`、`P2-GOLDEN-001`、`P2-LOW-RISK-WRITE-001` 的 `depends_on`；`docs/phase2/ARCHITECTURE.md` §8 的 D-5 / D-6 / D-7 三项由待裁决转为已裁决。
## 2026-08-19 — 裁决：Work Object 与 OA 的状态同步策略

**决定**：本系统存 OA 待办的状态，但**存的是「上次看到的样子」与「我对这件事做了什么」，不是「这件事现在是什么状态」**。正式业务状态永远以 OA 为权威。五项细则：

| # | 项 | 裁定 |
|---|---|---|
| 1 | 存不存 | **存**。不存则工作台无法在用户未打开时成立，超时提醒与优先级排序都失去依据。存的内容限定为：上次拉取到的 OA 字段快照 + 拉取时间戳 + 本系统自己的处理痕迹 |
| 2 | 何时同步 | **后台定时轮询 + 用户打开工作台时拉取 + 手动刷新按钮**，三者并存 |
| 3 | 两边不一致时界面以谁为准 | 显示**上次拉到的状态**，并在界面上**始终显示数据截至时间**，不藏在角落。不显示本系统自行推算的业务状态 |
| 4 | 用户标记已办但 OA 未变 | 本系统状态记为 **`待同步完成情况`** 这一明确中间态，语义是「用户声称已办，等 OA 确认」，**不等于完成**。完成状态只认 OA |
| 5 | 同步失败（OA 不可达、凭证失效） | 显示旧数据 + **醒目提示**同步失败与数据时间；凭证失效时直接引导用户重新绑定。不静默降级、不假装正常 |

**边界补充**：第 4 项存在一种 OA 永远不会变的情形——用户通过线下沟通或其他流程解决了该事项。因此除 `待同步完成情况` 外必须提供一个出口标记（如「已在别处处理 / 与我无关」），否则这类事项会永久卡在中间态。该出口只改变本系统的展示与排序，**不得**从待办列表中真正抹除 OA 仍然在办的事项。

**为什么**：2026-08-18「产品定位」把 Work Object 定为跨系统工作编排状态的权威对象，同时要求「不复制成第二套业务真相」。把存储内容限定为「上次看到的样子 + 我的处理痕迹」，是同时满足这两句的唯一形状：工作台有数据可用，而业务真相仍只有 OA 一份。第 3 项拒绝显示自行推算的状态，是因为一旦用户被误导过一次（以为未办、重复去办），工作台的可信度就不可恢复。

**影响面**：`P2-WORK-OBJECT-001` 的字段设计与状态机；工作台列表与详情的展示合同（数据时间戳为必显字段）；同步失败的降级展示；本条与下一条「凭证模型变更」共同解除 `P2-WORK-OBJECT-001` 的 BLOCKED。

## 2026-08-19 — 凭证模型变更：改为保存用户 OA 密码并支持后台定时轮询（过渡方案）

**决定**：凭证模型由「仅复用用户交互登录得到的 OA Session」改为**保存用户的 OA 账号密码**，首次使用时由用户输入完成绑定，系统据此在用户不在线时自动登录并定时拉取其待办。

**本条明确推翻两句既有约束**：`docs/phase2/PHASE2_PLAN.md` 中「凭证模型始终是每用户复用自身 OA Session，不用共享服务账号、不存密码、不静默重登」里的 **「不存密码」** 与 **「不静默重登」**。「不用共享服务账号」继续有效——每个用户仍用自己的账号，不引入共享账号。后续任何棒不得再按被推翻的两句设计。

**为什么可以这样做**：问责链条不由「谁持有凭证」承担，而由**界面确认卡**承担。写操作的唯一入口是用户在本系统界面上点确认，而用户要点它必须先登录本系统；因此写操作依然只可能在用户本人在场时发生，存不存密码都一样。存密码真正改变的只有「读」可以在用户不在场时发生——这正是后台轮询所需，而后台轮询是工作台超时提醒与优先级排序的前提（见上一条第 1、2 项）。

原「不存密码」约束防的是「系统可在用户不在场时以其身份操作」；该风险由 2026-08-03「决定一：写操作凭证与问责」的人工确认门独立封堵，与凭证存储方式无关。部署环境为纯内网，风险面进一步收敛。

**这是过渡方案，不是终局**：泛微 ecology9 提供官方应用级 Token 认证（`appid` + 应用密钥 + 系统公钥换取短期令牌，业务接口携带加密 `userid` 代表具体用户读取数据），雨爷已确认**许可证可以拿到，但相关接口仍在改造中、暂不可用**。因此：

- 凭证获取路径必须留接缝，**不得把「用密码登录」硬编码进业务逻辑**；切换到官方 Token 时应只改凭证获取实现，不改调用方；
- 官方 Token 路线登记为已知未来路径，接口改造完成后重新评估切换；
- 与本系统已有的 `IdentityMappingPort`（本系统用户 ↔ OA 用户标识映射）天然契合，切换时该映射可直接复用。

**随本条生效的硬约束**（缺一不可，实现棒不得省略）：

1. **密码加密存储，密钥与密文分离**，复用既有 `SecretProviderPort` 与 AES-256-GCM 落地方式；明文密码不得进入 Trace、ResponseEnvelope、日志、fixture、报告或任何错误信息，并须配置针对性的凭证 canary 测试。
2. **密码错误一次即持久失效**：自动登录返回密码错误时，立即将该用户凭证标记为失效并**从此跳过其后台轮询**，界面提示用户重新绑定；不得在下一轮询周期重试。理由是 OA 的登录失败锁定阈值与时长**当前未知**（OA 仅返回累计错误次数），在边界未知时任何重试都可能批量锁定用户账号。
3. **检测到验证码要求即停止轮询并告警**：OA 验证码是服务端可配置开关，当前关闭但随时可能开启；程序不得尝试绕过，须停止该用户轮询并提示需要人工介入。
4. **轮询须有频率上限、工作时段限制与失败退避**：初值定为每用户 10 分钟一次、仅工作时段轮询、连续失败按指数退避，并设全局并发上限。该初值为保守起点，须以内网实测的 OA 负载调整。
5. **不得因凭证失效自动切换到其他账号**，沿用 2026-08-18 及蓝图 §9.1.1 的既有禁令。

**未验证项**（不阻塞本决定，但须在实现或运维中确认）：OA 登录失败锁定的阈值与时长未知；每次程序登录是否在 OA 侧产生可见登录记录、是否更新在线状态未确认，应按「会产生审计记录」处理。OA 无验证码（未连续输错时）与无单会话限制两项由雨爷 2026-08-19 现场确认。

**影响面**：`P2-WORK-OBJECT-001` 的 BLOCKED 解除；新增用户 OA 密码绑定的前端入口与后端接口；`app/infra/auth` 与凭证存储的扩展属 A 档，涉及 DB schema 变更需专项授权；后台轮询任务需要 `JobQueuePort` 承载；2026-08-03「决定一：写操作凭证与问责」的人工确认门**责任加重**——它现在是问责链条的唯一支点，任何削弱该确认的提案都必须回到本条重新评估。
## 2026-08-19 — P2 收口标准修订：必达 / 机会 / 排除三层

**决定**：`PHASE2_PLAN.md` §1 原总目标「至少 1 个真实系统的部门试点纵切：先只读验收，再做 1 个获批的低风险写入」继续成立，但把原 IN 范围的 9 项**分成三层**，只有「必达」层决定 P2 何时收口。

**必达（缺一不可，全部达成即 P2 收口）**：

| # | 内容 | 承接 task_id |
|---|---|---|
| 1 | 一个真实系统（OA）的只读纵切，经 Gateway / Policy / Evaluator / Trace 全链 | 已完成 |
| 2 | Work Object 层 + 最小工作台：用户在浏览器里看得到自己的 OA 待办、当前状态与数据截至时间，可标记自己的处理痕迹 | `P2-WORK-OBJECT-001` |
| 3 | 后台定时轮询：用户不打开页面，状态也在积累 | `P2-OA-CREDENTIAL-POLL-001` |
| 4 | 一个获批的低风险写入，经确认卡授权、受版本绑定保护 | `P2-LOW-RISK-WRITE-001` |

**为什么要分层**：原范围把 9 项全列为必做，其中 DB Gateway 与 Memory 卡在第三方（DBA、业务/数据负责人）手里，而本项目无法保证他们何时给。若维持全部必做，P2 的收口时间将由项目外的人决定，实际后果是永远收不了口。分层后，收口只取决于本项目能自己推进的五项。

**同时修正一处内部矛盾**：`P2-GOLDEN-001` 原 `depends_on` 含 `P2-DB-GATEWAY-001` 与 `P2-MEMORY-001` 两个机会项，等于让必达项等待机会项。改为**覆盖当时已实现的路径**——做完哪块就考哪块，不等全部齐活。

**影响面**：`PHASE2_PLAN.md` §1 总目标段与 §2 IN 范围表；`P2-GOLDEN-001` 的 `depends_on`；此后任何「顺便把 X 也做了」的提案先对照排除清单。

## 2026-08-19 — 裁决：首个低风险写入定为 OA 待办事项审批同意

**决定**：`P2-LOW-RISK-WRITE-001` 的具体动作定为 **OA 待办事项的「审批同意」**。雨爷同期提到的「提交某个流程」作为增量，不在首棒范围。四项现场参数一并裁定：

| 项 | 裁定 |
|---|---|
| 测试环境 | OA **无独立测试环境**。首次写入必须使用**操作者本人名下的真实待办**，不得拿他人事项试验 |
| 授权层级 | 本阶段流程**本人点一下即生效**并自动流转到下一节点。本系统**不再叠加额外审批层**，确认卡即授权 |
| 回滚能力 | **不可自行撤销**。OA 侧只能由下一级审批节点退回，本系统无撤销接口可调 |
| 确认卡内容 | 显示姓名、流程标题、正文内容、附件列表名；默认只展示姓名与标题，卡片可展开查看更多 |

**因「不可自行撤销」而生效的硬约束**：

1. 确认卡必须**明示该操作提交后无法自行撤销**，只能由下一级节点退回；不得使用「可随时取消」一类表述。
2. Golden 必须包含对应负向用例：未经确认不得执行、确认后不得重复提交（幂等）、以及确认内容与实际提交内容不一致时拒绝执行。
3. 版本绑定（`P2-CONFIRM-BINDING-001`）是本棒硬前置——不可回滚的操作尤其不能出现「用户按 v1 确认、系统执行 v2」。

**影响面**：`P2-LOW-RISK-WRITE-001` 的 BLOCKED 解除并写入具体交付；HAR 素材已就绪，待 HAR 清洗脚本完成后可交付分析；「提交某个流程」登记为增量，不阻塞本棒收口。

## 2026-08-19 — 裁决：确认卡展示真实业务内容，不设字段白名单

**决定**：确认卡**展示真实业务内容值**，不再限制为只显示字段名，也**不设可展示字段白名单**。展示范围为姓名、流程标题、正文内容、附件列表名，默认折叠为姓名与标题，用户可展开查看完整内容。

**保留不变的一项**：凭证 marker 扫描继续生效——`sessionkey`、`datakey`、`password`、`token`、`cookie`、`sessionid` 等凭证字段一律不得进入 ResponseEnvelope、Trace、日志或 fixture。该禁令属 `AGENTS.md` 不可协商规则 4，不因本条放松。

**为什么这不是放松安全边界**：确认卡上呈现的内容，是该用户登录 OA 后**本来就能看到的自己名下待办的正文**——对他不构成新信息，因此显示它不产生新的泄漏面。原「只显示字段名」的做法（`P2-SDUI-CONFIRM-PAYLOAD-001`）防的是**参数值中混入不透明凭证**，而这一风险由凭证 marker 扫描直接封堵，与是否展示业务内容无关。再叠一层字段白名单，只会让每次新增展示字段都要改配置，属于对内网办公场景的过度设防；本项目在保证基本安全的前提下优先功能与体验。

**影响面**：`P2-SDUI-CONFIRM-PAYLOAD-001` 冻结的 `ui.payload` 四键结构需要扩展以承载业务内容与折叠态，属 A 档改动，由 `P2-LOW-RISK-WRITE-001` 或其前置棒承担；`app/runtime/runtime.py::_confirm_card_payload` 与 `app/infra/sdui/response_envelope_builder.py` 的凭证 marker 逻辑保持不变；既有的 marker-free 凭证 canary 测试必须继续通过。

## 2026-08-19 — 裁决：DB Gateway 移出 P2

**决定**：`P2-DB-GATEWAY-001` **从 P2 移除**，不再占据 DAG 位置，也不再作为 `P2-GOLDEN-001` 的依赖。后续确有需要时另行立项。

**为什么**：该任务的前提是「需要直连某个业务库并对获批只读视图开放查询」。经雨爷 2026-08-19 确认，本单位业务系统的数据**一律通过接口获取，不直连数据库**；每个人的权限由业务系统自身判定，调用方无权限时接口直接返回错误码，不需要本系统另建一套数据库层的权限控制。前提不成立，任务失去对象。

保留它只会持续产生两个后果：一是它作为 `P2-GOLDEN-001` 的依赖，让必达项等待一个永远不会到来的 DBA 批准；二是让清单读者以为 P2 仍有直连数据库的计划。

**不变的部分**：2026-08-03「决定二：数据库访问边界」继续有效——本系统自己的数据库不算「目标系统」，不进外部系统名册、不做 IdentityMapping、不加 `db` 枚举值，但 AI 对数据库的每次访问仍须在 Trace 里可查。本条移除的是「对外部业务库开放查询能力」这项任务，不是数据库访问的审计要求。

**影响面**：`PHASE2_PLAN.md` DAG 表移除该行并注明理由；BLOCKED 表「DB Gateway 真实纵切」一行标记为不再适用；`P2-GOLDEN-001` 的 `depends_on` 相应缩减；`ARCHITECTURE.md` §8.2 E-7 标记结项。

## 2026-08-19 — 裁决：知识库不进 P2；Memory 边界收窄

**决定**：**知识库不进 P2**，记入 P3。知识库指：个人与部门两级、可选查看权限、文档与 PDF 等文件转换为 Markdown 后入库、并支持检索的独立能力。它与 Memory 是两件事，不得混为一谈。

**Memory（`P2-MEMORY-001`）的边界**按雨爷 2026-08-19 裁定收窄为：

- **来源**：用户自定义编辑、日常聊天过程、办理业务过程中的记录；
- **用户画像**：除密码外原则上可记录，但**身份证号、银行账号、家庭住址等敏感个人信息不得进入 Memory**；
- **隔离**：部门之间必须隔离。

**为什么**：知识库涉及文件上传、格式转换、切分入库、权限模型与检索，规模不小于 Work Object 首棒，纳入 P2 会使范围再次显著膨胀，而 P2 的收口标准刚刚才明确。Memory 排除敏感个人信息，是因为 Memory 内容会随上下文进入 LLM 请求；身份证号一类信息一旦进入，既无业务必要，又会同时落入 Trace 与模型侧，扩大泄漏面且不可追回。

**影响面**：`P2-MEMORY-001` 的验收条件新增「敏感个人信息不入库」的负向测试；知识库登记为 P3 范围，`PHASE2_PLAN.md` 的排除清单同步；本条不改变 2026-08-18「产品定位」中三种工作表面的设计。

## 2026-08-20 — 裁决：每个前端棒的最低体验要求（三条）

**决定**：以下三条写入**每个前端棒**的 `done_when`，不满足即不算交付完成。

**一、三态齐全（硬要求）**。凡从后端取数据的页面或区块，必须交付三种状态：

- **加载中**：有明确加载指示，不留白屏、不让布局跳动；
- **空**：请求成功但无数据时，明确说明「确实没有」，不是留一片空白；
- **出错**：请求失败时明确告知失败，**不得用空列表冒充「没有数据」**。

**二、关键信息不折叠（硬要求）**。影响用户判断的信息必须直接可见，不得藏在展开区或次要位置。当前明确属于此类的：**数据截至时间**（2026-08-19「Work Object 与 OA 的状态同步策略」已裁定必须始终显示）、**逾期标记**、**同步失败提示**。

**三、不写死宽度（软要求）**。本阶段**不做**移动端专门适配（用户为办公室电脑），但不得使用固定像素宽度把布局堵死，以免将来上平板时重写。

**为什么单独立条**：这三类在开发时最容易漏——手上有测试数据，做出来的必然是「有数据 + 宽屏」那一版，其余状态需要专门设计才会存在。现有 `web/src/pages/admin/BindingsPage.tsx` 即是实例：后端失败时呈现空表格，用户会误读为「我没有绑定」。第一条第三项正是针对该类缺陷。

**影响面**：`P2-WORK-OBJECT-001` 及后续所有前端棒的 `done_when` 与验收证据；不改变任何既有安全边界。

## 2026-08-20 — 并行 lane 的测试库约束

**决定**：多条 write lane 并行时，**同一时刻最多一条 lane 可以新增 migration 并使用共享测试库**；其余 lane 必须使用各自独立的测试库。

**为什么**：本轮实测的失败模式——`P2-WORK-OBJECT-001` 将 `20260819_120000` apply 到共享测试库（`127.0.0.1:15432`），但该 migration 尚未提交到任何分支；`P2-PORT-SEAM-001` 从 `phase0/main` 起、自身一行 migration 都不加，基线仍因库中存在其 base 不含的 revision 而失败（`BLOCKED_PARALLEL_DB_REVISION`）。**即使某条 lane 完全不碰 migration，共享库被另一条污染后同样会红**，且此时任何需要跑测试的新棒都被连带阻塞。

原有的并行规则只覆盖了治理文档冲突，未覆盖测试库，因此该失败可重复发生。

**处置顺序**：出现该冲突时，**首选等待加 migration 的 lane 合入 `phase0/main`**——合入后库与 base 自然对齐，无需授权、无需新建容器。仅当等待代价过高时，才为其余 lane 配置独立测试库，且需雨爷专项授权；授权范围限于**新建空库并对其执行 migration**，**严禁对共享库执行 reset / downgrade / stamp**，亦不得修改仓库内任何数据库配置文件。

**影响面**：并行开棒前的判定项新增一条「本棒是否新增 migration」；A 档棒的启动提示词须写明测试库归属；`AGENTS.md` 的并行约束段落待下一次规则修订时吸收本条。
## 2026-08-20 — 裁决：办理按钮按自动化程度择一显示

**决定**：工作台上每个待办的办理入口，**按该事项的自动化程度只显示一个按钮**，不是三个并列：

| 按钮 | 何时显示 | AI 走到哪一步 | 人在哪一步介入 |
|---|---|---|---|
| **AI 办理** | 该能力可由 AI 全程完成 | 拟好全部内容并提交 | 提交前的确认卡；点确认才真正发出 |
| **AI 辅助** | AI 只能准备、不能提交 | 准备材料、给出建议 | 用户看完自行在页面上操作 |
| **回原系统办** | 该事项不支持自动化 | 不参与 | 全程在源系统内完成 |

**三者的差别是 AI 走到哪一步，不是要不要确认**——三种路径都不绕过既有的人工确认门。「AI 办理」不意味着无人确认，2026-08-03「决定一：写操作凭证与问责」的确认要求对它同样成立。

**默认必须 fail-closed**：能力未声明自动化程度时，一律显示「回原系统办」，不得默认按可自动处理。

**为什么**：三个按钮同时摆出会让用户每次都要自己判断该点哪个，而这个判断本应由系统根据能力声明作出。同时「AI 办理」这一措辞极易被读成「不用我确认」，故在决定中显式绑定确认门，避免实现时按字面理解省掉确认。

**影响面**：`CapabilitySpec` 需新增「自动化程度」声明字段（属 `app/ports/` 契约变更，A 档；已登记欠债）；工作台列表与详情的按钮渲染；未声明时的 fail-closed 分支须有负向测试。

## 2026-08-20 — 澄清：凭证模型适用于所有目标系统，不只 OA

**决定**：2026-08-19「凭证模型变更：改为保存用户 OA 密码并支持后台定时轮询（过渡方案）」的适用范围**不限于 OA**，而是**所有需要接入的目标系统**。雨爷 2026-08-20 确认：其余业务系统与 OA 同构——均有接口、均需先做 HAR 分析，保存各系统账号密码正是为此。

因此凭证模型的实际形态是：**每用户 × 每系统一套凭证**，而非每用户一套。

**随之明确的三件事**：

1. **绑定入口必须能管理多套凭证**，不是单一 OA 密码输入框；用户可分别绑定、更新、解绑各系统凭证，某一系统凭证失效不得影响其他系统。
2. **每接入一个新系统的成本 = 一轮 HAR 分析 + 一套凭证绑定**，这是排期与工作量估计的基准，`P2-HIKVISION-ADAPTER-001` 按此计。
3. 2026-08-19 决定所附的五条硬约束（加密存储且密钥分离、密码错误一次即持久失效、检测到验证码即停止轮询告警、轮询有频率上限与退避、不因凭证失效自动切换账号）**逐条适用于每一个系统**，不是只对 OA 生效。

**为什么单独澄清**：原决定通篇以 OA 为主语，标题、正文与影响面均写「用户的 OA 账号密码」。按字面实现会得到一个只支持单一系统的绑定入口，而真实需求是多系统多凭证——两者在数据模型、界面与失效处理上差别显著，不澄清必然返工。

**影响面**：凭证存储的数据模型（须以 `(用户, 目标系统)` 为键）；绑定入口的前端与后端接口；`P2-OA-CREDENTIAL-POLL-001` 的设计须为多系统留出结构，即便首棒只接 OA；官方应用 Token 的未来切换路径同样按系统逐个评估。

## 2026-08-20 — 事实确认：OA 中每个用户只能看到自己的待办

**决定**：确认 OA 的数据可见范围为**每个用户只能看到分派给自己的待办**（雨爷 2026-08-20 现场确认）。本项目采用每用户自身凭证访问 OA，因此从 OA 能取得的数据范围以该用户在 OA 中的权限为准。

**直接推论，后续棒不得再假设相反情形**：

- **监区、科室级的看板与统计，无法用 OA 待办数据实现**。任何基于 OA 数据的部门级聚合都拿不到本人以外的行。
- 部门级视图的现实数据源是**本系统自己派发的任务**（见同日「任务派发方案归机会层」）——那些任务的分派关系与完成状态由本系统掌握。
- 若将来确需从 OA 取得部门级数据，只有两条路：该用户在 OA 中本就具备部门查询权限（则用其自身凭证即可，属个案），或引入具备部门权限的账号——**后者与「不用共享服务账号」的既有约束冲突，须单独裁决**，不得默认采用。

**为什么落盘**：这是一个否定性事实，不写下来，后续棒会重复尝试「能不能从 OA 拿部门数据」并重复失败；而它同时是「首页看板区暂无数据」与「派发模块是看板唯一现实数据源」两项判断的唯一依据。

**影响面**：工作台首页的看板与统计区在派发模块落地前只能显示空态；`P2-HIKVISION-ADAPTER-001` 等后续 Adapter 的可见范围同样以用户自身权限为准，不得预设更大范围。

## 2026-08-20 — 裁决：任务派发方案归机会层，拆为两棒

**决定**：任务派发与统一待办方案（`_scratch/P2-INTERNAL-WORK-OBJECT-001_任务派发完整方案.md`，雨爷 2026-08-20 编写）归入 P2 收口标准的**机会层**——做，但不阻塞 P2 收口。方案按其 §4 拆为两棒，均为 **A 档**、串行、独占 worktree、必配监理、必过 Opus 桥：

1. **`P2-OA-ORGANIZATION-DIRECTORY-001`** —— OA 只读组织目录合同、本地组织镜像、可信 Principal 部门上下文、部门授权查询能力。
2. **`P2-INTERNAL-WORK-OBJECT-001`** —— Work Object 双权威模型、人工状态机、派发页面、统一待办、附件、审计与部门隔离验证。依赖前者。

**方案中已确立、本条一并生效的核心设计**：

- **不创建第二套任务对象**。人工派发的每一项任务、备忘、提醒都是现有 Work Object 的实例。
- **双权威判别**：`state_authority` 取 `external_snapshot`（OA 同步，业务状态权威在 OA，本地不得修改）或 `internal`（人工派发，权威在 EternalAI，可改派/开始/提交/退回/验收/取消）。同一聚合下的两个受判别状态模型，API、Port、DB 约束与页面动作须共同防止两种权威互相污染。
- **三条入口边界固定**：人工派发 → 直接创建内部权威 Work Object（**不经 `WorkCandidate`**、不调 Human Gate，发布前预览只做表单校验与防误操作）；正式 OA 待办 → 直接同步为外部快照权威；AI 从聊天/文件等非结构化内容推断 → `WorkCandidate` → 人工确认 → Work Object。
- **兼容式演进**：V1 对既有 OA 行仅做 schema default 与约束扩展，**不搬表、不重写 OA 业务字段**；未来若物理拆分 OA 快照表并搬迁既有行，属新的数据迁移 scope，须重新取得专项授权。

**为什么归机会层而非必达**：P2 收口标准的必达五项已于 2026-08-19 确定，派发模块不在其中，不应再次扩张必达范围。但它归机会层而非 P3，理由是同日「OA 中每个用户只能看到自己的待办」——**它是部门级看板与统计的唯一现实数据源**，工作台首页的看板区若要有真实内容，只能靠它。

**排期依赖说明**：方案 §2.3 要求等 `P2-WORK-OBJECT-001` 与 `P2-PORT-SEAM-001` 合入 `phase0/main` 后再开始。前者已于 2026-08-20 合入。**对 `P2-PORT-SEAM-001` 的等待是排期上的串行安排（避免并发触碰 `app/ports/` 与 migration 名额），不是技术依赖**——两者在功能上无耦合；若 `P2-PORT-SEAM-001` 长期不排期，可另行裁定解除该等待。

**已授权与仍需授权**：方案 §19 记录雨爷已授权本模块所需的**可逆 schema migration**；未授权任意生产数据重写、数据搬迁、新增第三方依赖、修改 `.env` / 真实凭证 / 冻结蓝图 / Golden fixture，亦未授权删除、rebase、reset-hard、force push 或生产部署。

**外部输入前置**：`P2-OA-ORGANIZATION-DIRECTORY-001` 需先以只读 OA 页面 HAR 固化人员与部门的稳定 ID、部门层级、归属关系、唯一主负责人、分页与快照结束条件等事实。方案已定 fail-closed 边界：**若只能取得姓名或无法确认完整性，停止实现并报告，不得创建猜测式映射**。

**影响面**：`PHASE2_PLAN.md` 收口标准机会层与 DAG 各新增两项；`Work Object 的 source_system 写死为 Literal["oa"]` 一条欠债由 `P2-INTERNAL-WORK-OBJECT-001` 承接；方案文档保留在 `_scratch/`，不进仓库，正式合同以本条及后续实现棒的产出为准。
## 2026-08-20 — 裁决：Excel / HR 批量映射导入划入 P3，并修正 IN 段的失真表述

**决定**：账号映射的 **Excel / HR 批量导入**不在 P2 做，划入 P3。同时修正 `PHASE2_PLAN.md` §2 IN 段中「支持 Excel/HR 导入映射」一句——该表述自 `P2-PLAN-001` 起一直在列，但当前**既无实现、无 task_id 承接，也无任何决定说明其去向**。

**为什么划 P3**：P2 只接入 OA 一个真实系统（第二个系统海康属机会层且外部输入未到）。单一系统下逐人手工绑定即可满足试点规模，批量导入的价值出现在多系统、多人、需按 HR 名册批量建立映射时，而这些前提在 P2 均不成立。

**为什么必须同时改 IN 段**：这是本次核查发现的唯一一类「无声缺失」——蓝图要求（对应核查报告 A23 / A42）、IN 段逐字写着要做、实际无人承接。**纸面声称在做而实际没做，比明确不做危险得多**：读文档的人会以为已有承接，不会再追问。

**成因（已追溯，记录以防重演）**：该能力原属 `P2-PILOT-OPS-001`（初始提交 `8d2e104` 中其描述为「交付**绑定管理/映射导入**、审计看板和最小反馈统计的试点运营面」）。2026-08-18「`P2-PILOT-OPS-B-001` / `C-001` 并进工作台」与 2026-08-19「`P2-PILOT-OPS-001` 拆解与工作台 DAG 重排」两次决定均称剩余范围「由工作台节点承接」，但实际承接的 `P2-WORK-OBJECT-001` 范围内并无绑定管理与映射导入。**这是一次承接落空：拆解时写了承接方，承接方的 scope 里却没有它。**

**由此确立的一般规则**：任何棒被拆解或合并时，**其原始交付描述中的每一项都必须显式指明去向**——由哪个 task_id 承接、推迟到哪个阶段、或明确取消。不得只写「剩余范围由某某承接」而不逐项对照。

**影响面**：`PHASE2_PLAN.md` §2 IN 段该行修正；批量导入登记为 P3 范围；`P2-PILOT-OPS-001` 拆解行补注去向说明。

## 2026-08-20 — 裁决：凭证存储的多系统改造并入 `P2-OA-CREDENTIAL-POLL-001`

**决定**：凭证存储由「每用户一行」改为「**每用户 × 每目标系统一行**」的表结构改造，**并入 `P2-OA-CREDENTIAL-POLL-001`**，与该棒的密码绑定、加密存储一并完成，共用一次 migration。

**为什么现在就要定**：2026-08-20「澄清：凭证模型适用于所有目标系统，不只 OA」已确立实际形态是每用户 × 每系统一套凭证。但现行 `oa_session_credentials` 表以 **`ai_user_id` 为单主键**（`alembic/versions/20260724_090000_auth_credentials.py`），同一用户同一系统只能存一行，更无法区分系统——**该决定在当前 schema 下落不了地**。

**为什么并入而非独立成棒**：`P2-OA-CREDENTIAL-POLL-001` 本就要改动凭证存储（新增密码绑定与加密存储），主键调整与之共用一次 migration 即可；拆成两棒则要对同一张表连续做两次结构变更，成本更高且中间态无意义。

**该棒须一并满足**：主键或唯一约束以 `(用户, 目标系统)` 为准；某一系统的凭证失效不得影响该用户其他系统的凭证；绑定入口能分别绑定、更新、解绑各系统凭证。即便首棒实际只接 OA，**结构必须为多系统留出位置**，不得再以单系统假设建表。

**影响面**：`P2-OA-CREDENTIAL-POLL-001` 的 Scope 与 migration；`app/infra/auth/postgresql.py::PostgreSQLCredentialStore`；`app/infra/identity/postgresql.py::PostgreSQLOAIdentityMapping` 的投影键；DB schema 变更属红线，该棒开工前需确认已获专项授权。

## 2026-08-21 — 裁决：Golden 拆两棒，解开与低风险写入的 DAG 循环

**决定**：`P2-GOLDEN-001` 拆为两棒。`P2-GOLDEN-001` 只冻**当时已实现**的路径（真实只读、Work Object 与工作台、确认绑定与版本锁定、隔离、审计与反馈的负向边界），不等写入。**⚠ 2026-08-28 起本括号内的枚举已被收窄**：「Work Object 与工作台」「隔离」「审计与反馈」三项不进 Golden，归 API 与单元层，见同日「必达项 5 的完成判据口径」；本句其余部分继续有效，**不得据此括号枚举设计新的 Golden 题面**。`P2-LOW-RISK-WRITE-001` 落地后另开 `P2-GOLDEN-002` **增量**冻写入路径。必达项 5 需两棒都完成才算达成。

**为什么这样解**：2026-08-19 的原裁定已确立「**做完哪块就考哪块**」，拆棒是该原则的直接落地，不是新原则。相反方向（删掉写入棒对 Golden 的依赖、最后一次性冻全部）会让风险最高的一棒——真实 OA 写操作、本人确认即生效、**不可自行撤销**——在整个开发期内失去 Golden 回归保护，与「负向/边界路径必须 100% 通过」的不可协商规则相悖。

**边界**：`P2-GOLDEN-002` 是增量，不得原地改写 `P2-GOLDEN-001` 冻结的题面；两棒的 fixture 与 `FROZEN_GT_IDS` 各自须经雨爷显式批准（2026-08-03「决定四」继续适用）。

**影响面**：`PHASE2_PLAN.md` 的 DAG 与 `depends_on`；`P2-LOW-RISK-WRITE-001` 的阻塞状态；必达项 5 的完成判据。

## 2026-08-21 — 裁决：门禁覆盖性写入验证策略

**决定**：`AGENTS.md`「验证策略」段新增**门禁覆盖性**要求——要求运行某项门禁时，须同时给出该门禁实际走到本次改动路径的证据；判据是「把本次改动全部回滚，该门禁还会绿吗？会绿即说明它没有覆盖改动」。门禁绕开改动路径时，补齐接线属加强、计入本棒范围。

**问题（实例）**：`P2-CONFIRM-BINDING-001` 首轮，启动提示词以「触及确认/恢复/执行的运行时语义」为由要求跑 Golden gate。实现方跑了、监理独立重跑、主窗口抽查，三方都得到全绿。但 `scripts/golden_task_evaluator.py` 的 `build_runtime(...)` 当时**根本不传 `human_gate_port`**，Golden 跑的是未接新 Port 的 runtime——那份绿对本棒新路径零证据。且 Port 一接上，GT-024 冻结的裸「确认」交互即失效，属本应触发停手报告的情形，却被这份绿掩盖过了三道关卡，最终由 Opus 评审桥截住。

**为什么要成为规则**：这与既有的「验收项写进提示词不等于会被验」不是同一类。那类是**有没有验**，本条是**验了、数字也真、但证明的不是要证明的东西**。三方独立重跑同一个不覆盖的门禁，只会得到三份同样无效的证据，人数和重跑次数都不构成补救。

**边界**：本条要求的是覆盖性证据，不是更多门禁——不得据此把定向验证扩成固定全量套餐，验证仍按触碰面选择最小充分集合。补接线属加强，但 fixture 与 `FROZEN_GT_IDS` 仍须人工显式批准，不得以改题换绿。

**影响面**：`AGENTS.md`「验证策略」段；此后各棒启动提示词的验证章节与监理检查表。

## 2026-08-21 — 裁决：个人备忘的隐私边界，管理员不得读取他人备忘

**决定**：管理员（`admin`）**不得**读取他人的个人备忘/提醒及其正文与附件。任务派发方案 §7.2 授权矩阵中 admin 对「个人备忘/提醒」一列的「是」改为「仅自己」，与 §7.1 的「仅本人可以列表、查看、操作和下载附件」对齐。

**问题**：方案 §7.1 与 §7.2 直接矛盾。按 §7.2 矩阵实现，管理员可读任意人的私人备忘正文与附件；按 §7.1 则不可。同一列中普通用户写「仅自己」、部门负责人写「自己」、admin 写「是」，三种写法混用，实现方必然要猜。

**为什么这样定**：个人备忘的产品含义就是私人的；admin 的职责是管理部门工作对象，不是读取他人私人记录。授权矩阵不得成为隐私边界的后门。

## 2026-08-27 — 裁决：部门层级在授权中的作用（上级可看下级，可跨层派发）

**决定**：组织部门树中，**上级部门的主负责人对下属各部门拥有查看权与跨层派发权**。

- **查看**：上级部门主负责人可以看到其下属各级部门的全部 Work Object；
- **派发**：可以直接把任务派给下属部门中的任意成员，不必经由该部门负责人转派。

范围沿部门树向下递归，不限一层。同级部门之间无互相查看权。非主负责人只有本部门范围。

**为什么**：`PHASE2_PLAN.md` 登记的欠债「部门层级在授权中的作用未定义」——任务派发方案 §5.2 建了 `organization_departments` 父子关系，但 §7 授权模型只有「本部门」概念、从不引用层级。按字面实现即「没有层级」，监区→科室这类形态下监区主负责人将什么都看不到，不是预期行为。雨爷 2026-08-27 裁定按实际管理关系实现。

**实现要求**：

1. `AuthorizedWorkObjectScope` 必须承载**递归的部门子树**，不是单个 `department_id`；
2. 递归深度不设上限，但必须防环——组织目录导入时若检测到部门父子成环，**fail-closed 报错，不得静默截断**；
3. 必须有**跨层负向测试**：同级部门之间不可见、下级不能反向查看上级、非主负责人不得跨部门；
4. 越权拒绝要落审计（`P2-INTERNAL-WO-SCOPE-001` Scope 内已有该项）。

**影响面**：`P2-INTERNAL-WO-SCOPE-001` 的欠债结项，该棒 Scope 增加「递归子树 + 防环 + 跨层负向测试」；`P2-OA-ORGANIZATION-DIRECTORY-001` 必须固化部门父子关系与唯一主负责人（其 fail-closed 边界不变）。

## 2026-08-27 — 裁决：双权威 migration 的可逆性边界（downgrade 删内部数据，但须显式守卫）

**决定**：`P2-INTERNAL-WO-MODEL-001` 的双权威 schema migration，其 `downgrade` **允许删除表中的 internal 行**以使结构回滚总能成功。雨爷 2026-08-27 就此删除动作单独授权，**授权范围仅限该 migration 的 downgrade 路径**，不构成任何其他删除数据的授权。

**但必须加显式守卫**：`downgrade` 中的 DELETE 只在环境变量 `ALLOW_DESTRUCTIVE_DOWNGRADE=1` 时执行；未设置时**报错退出**，错误信息须写明「表中存在内部任务数据，结构回滚将删除它们；确认后设置 ALLOW_DESTRUCTIVE_DOWNGRADE=1 重试」。

**为什么**：`PHASE2_PLAN.md` 登记的欠债——`downgrade` 要把 7 个 OA 列改回 `NOT NULL`、加回 `source_system='oa'` check，表中一旦存在 internal 行必被 PostgreSQL 拒绝。两个选项各有代价：只回滚结构则 downgrade 在有数据时必失败；删数据则 downgrade 总能成功但有误执行风险。雨爷选后者。

守卫是执行棒的工程补充，不改变裁定方向：它让「downgrade 总能成功」在**开发与测试场景**成立（设一次环境变量即可），同时使**生产误执行**不会静默清空任务数据。删除动作仍然发生，只是要求一次显式确认。

**验证要求**：

1. 空表 downgrade 成功（不需要环境变量）；
2. 仅有 OA 行时 downgrade 成功（不需要环境变量）；
3. 有 internal 行且**未设**环境变量时，downgrade **报错退出且数据完好**；
4. 有 internal 行且**已设**环境变量时，downgrade 成功且内部行被删除。

四条都要有测试，第 3 条是守卫本身的证明。

**影响面**：`P2-INTERNAL-WO-MODEL-001` 的欠债结项，Scope 增加守卫与四条 downgrade 测试；`tests/db/test_migrations.py` 的 upgrade→downgrade→upgrade 循环测试须覆盖有数据场景。

### 三、软件中心、消息与外部系统工作区

**软件中心 `/apps`** 分三块：

### 四、AppShell、顶栏、搜索与空状态

桌面 AppShell 为左导航、主内容、AI Dock 三栏；页面标题放主内容顶部，不占顶栏。以 1280px 为核算基准：左导航约 200px 后顶栏可用约 1080px，搜索 280px + 组织范围 140px + 右侧信号与间距约 190px，仍有余量。左导航可折叠为图标条并持久化；Dock 是跨路由的 **AppShell 单例**，不把任一页面写成固定死宽；响应式分档本阶段不实现。

附注：AI 共事空间的「主导航 + 会话列表 + 对话/产物 + 上下文检查器」若全部常驻，在 1280px 下中间区只剩约 560px，**实测核算不成立**；完整三栏常驻只在 `>=1600px` 成立，较窄时须折叠主导航和上下文检查器。本附注不扩大 P2 范围。

顶栏的**系统状态**与**通知**是两类信号，不合并计数。任一目标系统凭证失效或过期时，系统状态显示红点 + 数字，展开后列出系统状态与重新绑定动作；事项提醒、系统告警与将来的消息未读数不得伪装成同一数字。组织范围只读显示，不做全局选择器。顶栏 AI 入口只做「打开 Dock」，在落地页、将来的共事空间与问一问不渲染。

P2 全局搜索只搜 Work Object，精确字段为**标题、来源编号、责任人**；搜索结果必须走与列表完全相同的授权范围。禁止 AI 补全、语义改写或「猜你想问」；跨消息、材料、会话搜索不进 P2。搜索结果可把命中集注册为 Dock 上下文，但检索负责找到、AI 负责理解，两者不合并输入框。

**空状态统一规范**：工作事项列表、软件中心、搜索结果都必须说明**为什么为空 + 用户下一步能做什么**，不得只写「暂无数据」。这条就地补齐讨论稿对不存在的「§9 空状态」的悬空引用；它直接约束本条已裁定的三个表面，不另登记无主欠债。

### 五、工作事项列表、工作室与办理按钮

列表主行固定四列：`标题 / 责任人或责任部门 / 截止时间 / 下一动作`。灰色副行固定为 `来源系统 · 来源编号 · 当前步骤 · 数据截至时间`，必须常驻可见，不得靠 hover。Trace / Evidence、完整阻塞说明、附件只进工作室。

外部快照与内部权威用**动作集 + 来源徽标**表达，不暴露 `external_snapshot` 等内部词：外部快照只有「查看 / 去 OA 办」，没有「开始 / 提交 / 退回」；行首显示 `OA` / `内部` 来源徽标。AI 结果默认只是会话产物，只有用户显式保存后才成为 Work Object 的共享结果。

办理入口继续只显示一个大白话按钮，现役文案为 `让 AI 先写` / `我自己办` / `去 OA 办` / `先看看`；这些文案**取代**讨论稿的旧四按钮文案。`AI 写的，还没确认` 也取代旧角标「AI 草稿」。Dock `pinned` 时列表自动切为紧凑双行，不横向滚动、不隐藏列。

2026-08-20「按自动化程度择一显示」的引用日期在本条初版误写为 2026-08-21，现更正为 **2026-08-20**。现役代码中 `app/ports/capability_registry.py::CapabilitySpec` 没有自动化程度；`type`、`risk_level`、`binding_required` 分别表示能力形态、风险和绑定前置，均不能替代该维度。`app/ports/work_object.py::WorkObjectRecord` 也没有办理 capability 映射；`app/api/v1/work_objects.py::WorkObjectService._sync_for_principal` 的固定 OA capability 只负责同步列表，`app/runtime/runtime.py::_select_capability` 则从自然语言意图选能力，都不是 Work Object 行的办理映射。

因此单立 **A 档** `P2-CAPABILITY-AUTOMATION-LEVEL-001`，范围不是只加字段，而是同时完成：

1. `CapabilitySpec` 新增 `full` / `assisted` / `manual` 自动化程度；未声明时 fail-closed 到 `manual`（回原系统办）；
2. 建立 Work Object → 办理 Capability 的映射合同；
3. 工作事项列表按自动化程度、映射结果、当前步骤与来源权威确定性投影为上述四个按钮之一，未知组合不得猜测为可自动办理。

该 A 档棒必须先于 `P2-FE-WORKBENCH-001`，避免工作台把按钮写死后再返工。

### 六、AI Dock、会话阶段边界与页面上下文安全合同

本次修订**取代**初版「三态 + `/ai/sessions/:id` 跳转并须从 `sessionId` 冷启动恢复」：

1. 会话持久化整体推迟 P3。P2 不扩 `sessions` 表、不建会话 API、不做会话列表。
2. P2 Dock 仍保留 `closed` / `drawer` / `pinned` 三态，但界面只暴露开/关。`drawer` 是不改变主内容宽度的浮层；`pinned` 推挤主内容并跨页面保持；`closed` 只隐藏，不把关闭误写成持久会话删除。
3. Dock 必须是 AppShell 单例；展示模式与**当前 P2 临时会话状态**放在非持久化 Zustand store，保证普通 SPA 跳转不换 `sessionId`、不丢当前对话。这一现役分工取代 A 稿原来的「`drawer` 只放内存、`pinned` 展示放 Zustand、会话放 Query cache」：P2 没有可缓存的服务端会话，三态展示与当前临时会话统一归 Zustand，其他服务端状态仍归 Query；Zustand 不得复制未来的持久会话历史。
4. P2 **不做** `/ai/sessions/:id` 路由。一个刷新即失效的 URL 会被收藏、转发，却只能打开空内容，是产品陷阱。
5. 「须能从 `sessionId` 冷启动恢复」整条移到 P3，与会话持久化同批。

**为什么**：`alembic/versions/20260604_090000_task_session_schema.py::upgrade` 创建的 `sessions` 只有 `session_id`；`app/ports/task_store.py::SessionStorePort` 只有 `create_session` / `get_session`；仓库没有对话原文持久化。`web/src/pages/ChatPage.tsx::ChatPage` 挂载时以 `crypto.randomUUID()` 生成局部 `sessionId`，而 `web/src/App.tsx::AppShell` 的路由切换会卸载子页面；`web/src/stores/` 现只有 `authStore` / `roleStore`。所以丢失不需要刷新，普通路由切换就会发生；AppShell 单例与 Zustand 是 P2 内解决当前会话连续性的最低充分边界，不等于历史持久化。

页面向 Dock 注册的上下文固定为九字段：`surface_id`、`organization_scope`、`work_object_refs`、`source_refs`、`filters`、`selected_metric`、`allowed_capabilities`、`freshness`、`visibility`。这是 Port 与安全边界，不是每个页面自行拼装的 UI 细节；单立 **A 档** `P2-PAGE-CONTEXT-CONTRACT-001`，无前置，并须先于第一个真正注册上下文的 `P2-INTERNAL-WO-DISPATCH-001`。

Dock 上下文禁止：不得投整个 DOM、隐藏表格行、其他页面缓存或不可见字段；切页必须显式提示「上下文已切换」；继续旧会话时只携带用户确认的摘要与引用；跨部门或数据范围默认新会话。Dock 内容顺序固定为：当前上下文与权限范围 → 页面快捷动作 → 当前会话 → 结构化结果卡 → 保存/预览/确认/展开 → 输入区。

### 七、任务交办

任务交办保持单一入口顺序式：自然语言输入 → 同页展开预填表单；用户也可直接填写，不做两个并列入口或切换 Tab。发布前固定展示九类字段：类型、标题、责任人或责任部门、截止时间、办理要求与交付物、回执要求、提醒策略、可见范围、批量目标解析与去重结果。**AI 草稿不等于发布**，发布必须是显式人工动作。

表单固定使用 RJSF 已验证的标准密度；若要塞进 Dock 或其他紧凑场景，必须先重跑紧凑密度 PoC，不得外推既有结论。

### 八、前端目录、状态与 API 边界

目标目录树与职责固定为：

```text
web/src/
├─ app/         AppShell、routes、providers、navigation；不放业务字段拼装
├─ features/    页面与用例编排；不手写跨域 API client，feature 间不互相 import
├─ entities/    领域展示模型与通用组件；不复制服务端状态仓库
├─ shared/      api、auth、query、ui、formatting、errors；不反向依赖 feature
├─ contracts/   JSON Schema / OpenAPI 派生的语言中立协议；不依赖渲染器
└─ generated/   Orval 生成物；禁止手工编辑
```

迁移不开 47 文件搬迁棒：首个新 feature 只建 `features/work-dispatch/`，老代码原地保留；第三个 feature 出现时再评估收编存量。除既有三条依赖守卫外，新增第四条：**新增页面代码不得再进入扁平 `components/` / `pages/`**。

引入 `contracts/` 的棒必须同时落架构守卫：`contracts/**` 不 import `react` / `antd` / `@ant-design/*`；`shared/**` 不 import `features/**`；`features/A/**` 不 import `features/B/**`。

状态职责四分：服务端状态、缓存、刷新与轮询归 TanStack Query；导航折叠、Dock 展示和本地草稿归 Zustand；可分享、可恢复的筛选、视图、选中对象与页签归 URL；组件内短生命周期归 React local state。P2 当前 Dock 临时会话状态按本条第六节放 Zustand，但**不得把 Work Object 或未来的持久会话历史复制进 Zustand 形成第二份真相**。

业务 API 优先 OpenAPI + Orval；组件中不直接写 `fetch` / `axios`；流式响应只允许一个受控传输适配层；结构化动作使用明确 DTO 与确认状态，不从自然语言推断授权；前端只消费后端授权结果，不重写权限规则。

### 九、命名、状态色与现役文案

| 用户看到 | 内部对象 |
|---|---|
| 功能 | `Skill` / `Capability` |

## 2026-08-27 — 裁决：低数字素养用户的界面硬约束

**决定**：终端用户为机关干警与科室文员，**部分人使用 Word 排版都很勉强**，年龄层偏大。以下约束对**所有前端棒**生效，写入各棒 `done_when`。

**先明确一条判断前提**：低数字素养 **≠** 低理解力。他们理解「给张三派个活、周五前交、要回执」，不理解的是**界面隐喻**。因此方向不是削减功能（削了会退回原系统），而是**把界面语言换成他们已经会的**。

### 一、有规范原文支撑的（强）

| 约束 | 出处 |
|---|---|
| 正文 **19px**、辅助文字不低于 16px | GOV.UK Frontend v6 大屏正文 19px/25px；HHS《Health Literacy Online》：至少 16px，老年用户较多时 19px |
| 行高约 **1.4**（130–150%） | HHS 同上。**注意**：WCAG SC 1.4.12 的 1.5 倍是「用户覆盖样式后不得丢内容」的兼容性测试，**不是默认排版值**，不得误用 |
| 文本对比度 **≥4.5:1**（大文本 3:1） | WCAG 2.1 AA SC 1.4.3。**「辅助文字」不是豁免理由**——只要用户必须读它，它就是普通文本。placeholder 同样适用 |
| 点击目标 **≥44×44 CSS px** | WCAG 2.1 **AAA** SC 2.5.5。**桌面鼠标不构成放宽**（pointer input 含 mouse）。辨析：WCAG **2.2** 新增 AA SC 2.5.8 基线为 24×24，两个数不得混写 |
| 中文正文每行 **≤40 个字形** | WCAG 2.1 AAA SC 1.4.8（拉丁文 80 字符，CJK 40 字形）。只用于连续阅读的长文本，不用于表格与卡片网格 |
| **禁止用 placeholder 代替可见标签** | GOV.UK Text input：输入后消失、读屏不一定读取、默认对比度常不合格 |
| 高后果提交须**可逆 / 自动检查 / 提交前复核**三选一 | WCAG 2.1 AA SC 3.3.4。工信部《互联网网站适老化通用设计规范》2021 对法律承诺/财务交易另规定 **10 分钟内可撤销或修改** |

**「派发任务给他人」按高后果提交对待**：提交前复核面板（逐项可改）+ 发布后短时撤销条。**不得**使用「你确定吗？[确定][取消]」式同质对话框——重复、无差别的对话框会产生习惯化（Vance 等 fMRI + 三周现场实验）。

工信部 2021 年计算机网站配套要求同时进入验收：支持全程键盘和特大鼠标；提供网页放大与大字；焦点状态明显；关联控件有用途说明；非文本控件能说明用途；组件关系与层级清楚；避免诱导按键；告知当前位置与状态；支持撤销上一步；兼容主流浏览器、操作系统和辅助软件。

排版数值的适用边界补齐如下：WCAG 2.1 AAA 普通文本 `7:1`、大文本 `4.5:1`；大文本指至少 18pt，或至少 14pt 且粗体。SC 1.4.12 的 1.5 倍行高、2 倍段后距、`0.12em` 字间距与 `0.16em` 词间距是**用户覆盖后的兼容性测试**，中文不使用的词间距可按语言例外处理。44×44 CSS px 的 AAA 目标尺寸允许同页等价大目标、行内链接、未改尺寸的浏览器原生控件或不可替代呈现等例外；WCAG 2.2 AA 的 24×24 CSS px 也可按目标间距例外满足。不得把不同版本、等级与例外混写成单一强制数字。

### 二、有证据但需限定的（中）

- 这类用户较多**逐词阅读、较少扫描**，倾向按分类浏览而非搜索（HHS 汇总研究，对象主要为英文健康内容）；
- **陌生、无标签图标风险高**，W3C COGA 的做法是**熟悉图标与文字并置**——注意：「图标基本失效」是过度表述，证据不支持；
- **折叠区有遗漏风险**：GOV.UK 明确禁止把所有用户都需要看的内容放进 accordion。注意：「折叠等于不存在」同样是过度表述。**技术可访问 ≠ 认知可发现**——USWDS accordion 通过 WCAG AA 组件测试只证明接线正确，不证明低素养用户会发现里面的内容。

大型自然语言输入对低数字素养用户**可能降低命令与菜单学习门槛，也可能造成启动障碍，不能默认天然有利**；「空白框会造成恐惧」没有直接量化证据。缓解模式为：永久可见标签 + 短 hint、多入口浏览、明显提交按钮、拼写容错与自动完成、逐个引导问题、可见示例与模板。它们有规范或相邻场景支持，但缺少针对本项目场景的头对头效果量，不得声称某一方案已被证明最优。

确认框结论也须保留限定：重复、无差别、外观同质的警告会降低注意，但现代且情境明确的警告仍可能有效，失败原因不只「用户不阅读」。因此禁的是把同质「确定 / 取消」当唯一防错措施，**不是禁一切确认**。

高后果动作应组合：输入时阻止无效选择；接受多种格式并只在可靠时自动纠错；明确说明动作结果与不利后果；复核时给出对象与内容摘要；按钮使用明确动作名；允许返回修改；可行时提供短时撤销。

### 三、明确没有依据的（不得当作依据引用）

- **「7±2 个选项」无科学依据**：Miller 1956 研究的是单维刺激绝对判断与短时记忆 chunking，**未测试菜单**；选择过载元分析（Scheibehenne 等 2010）平均效应接近零。**同屏选项数量没有规范或实证上限。**
- **「三次点击法则」不成立**，非规范亦非可靠人因阈值。
- **「低素养用户很少滚动」证据不足**——能确认的较弱版本是：滚动后更容易丢失阅读位置并跳过内容。
- **中国桌面端中文正文无官方最低 px 值**：工信部规范的 18dp/pt 明确属**移动端**条目，不得移植为桌面强制值；对计算机网页只要求提供放大与大字屏幕服务。

以下 13 项是本轮查过但**没有可靠依据**的负知识：

1. 中国地方机关固定桌面、低数字素养用户的导航迷失层级阈值；
2. 「广而浅」与「当前位置感」的相对效应量；
3. 中国桌面端中文正文的官方最低 px 值；
4. 中文方块字对该人群的最优默认字间距；
5. 桌面政务界面同屏可选项的统一上限；
6. 「很少滚动 / 认为首屏以下不存在」的发生率；
7. 搜索或自然语言输入时使用完整句而非关键词的比例；
8. 点击犹豫、怕点错的犹豫时长与放弃率；
9. 空白大输入框造成恐惧的直接实验，以及示例、模板、引导问题三者的头对头比较；
10. 中国政务机关低数字素养桌面用户对对话式 AI 的长期接受度；
11. 撤销、二次确认、提交前预览三者跨任务的统一效果排名；
12. 「发送给领导 / 派发他人」这一社会后果动作的专项实证与政府设计标准；
13. 澳大利亚联邦 Government Design System 可稳定访问的现行组件级原文。

**以上 13 项不得被引用为设计依据；如需依据，须重新调研并给出出处。**

### 四、一条对本项目有利的规范澄清

GOV.UK 自述 **「one thing per page」不是普遍法则**，用户研究可支持合并页面，其举的例子正是**「需要快速重复和切换任务的政府内部服务」**。本项目属该类，故「今日工作并入工作事项」「任务交办单页顺序式而非向导」两项有规范支撑，不只是设计偏好。

**影响面**：所有前端棒的 `done_when` 增加本条；`web/` 的设计 token 按 §一 调整。相关讨论稿已获批弃置；本条已逐项承载其硬约束、证据边界、负知识与规范澄清，是这些结论的永久载体。

## 2026-08-27 — 裁决：cursor 分页合同移出 MODEL-001，该棒解除对组织目录的依赖

**决定**：

**问题**：2026-08-21 拆四棒时，各棒对组织目录的依赖是**从原大棒整体继承**的，未逐棒重新判定。2026-08-27 的独立核查确认：拆棒记录只为「第 2 棒起」写了授权模型理由，**未找到一份逐棒、逐 Scope 判定组织目录依赖的记录**；正式 DAG 把原整体前置放到链首，形成传递依赖。

逐项核查后，MODEL-001 五项中：

| 工作项 | 需要组织目录？ | 依据 |
|---|---|---|
| 双权威 schema 改造 | 否 | 目标是放宽 OA-only 约束、增加判别字段；`owner_department_id` 未定义为 `organization_departments` 外键 |

| `ON CONFLICT` 适配 | 否 | 只取决于外部快照的唯一索引形状 |
| **cursor 分页合同** | **是** | 原方案要求 cursor 绑定 `AuthorizedWorkObjectScope` 摘要，而 scope 定义为「可信 Principal + 当前组织目录 → scope」 |

**为什么移出而不是保留依赖**：

1. **D-6 已裁定首版列表不做服务端分页与排序、前端一次取回**。现有实现是「固定多取一条的有界批次」，不是分页。现在做 cursor 属超前工程；
2. cursor 绑定的 `AuthorizedWorkObjectScope` 是 `P2-INTERNAL-WO-SCOPE-001` 的产物。把它放进 MODEL-001 是**倒置依赖**——第一棒要消费第二棒尚未定义的对象；

**移出后的效果**：MODEL-001 不再消费任何组织目录产出，可在组织目录 HAR 采集完成前开工。SCOPE / DISPATCH / ATTACHMENT 三棒对组织目录的依赖不变。

## 2026-08-27 — 裁决：聊天附件与 Work Object 附件的边界

**附件子系统的存储层与授权层必须分离。**

- **存储层**（两阶段上传、类型与签名校验、ZIP 结构校验、每用户配额、私有存储）与授权主体无关，对聊天附件与 Work Object 附件是同一套；
- **授权层**（谁能下载这个附件）的**授权主体是参数，不是常量**。`P2-INTERNAL-WO-ATTACHMENT-001` 首版只实现 Work Object 一种授权主体，但**不得把 Work Object 写死进存储层接口或表结构的非空外键**。

**本条不扩大 `P2-INTERNAL-WO-ATTACHMENT-001` 的交付范围**——它仍然只做 Work Object 附件，不实现聊天附件。本条只约束其实现形态，使聊天附件将来能复用存储层而无需拆改。

## 2026-08-27 — 裁决：外部系统接入、录制路径与任务交办插槽应用

### 一、OA 页面内嵌 iframe 实测排除

2026-08 采集的四份 OA HAR 样本逐条解析响应头，结果如下；表中只记录响应头名与状态，不记录任何 Cookie 或凭证值：

| HAR | `X-Frame-Options` | CSP `frame-ancestors` | Set-Cookie |
|---|---|---|---|
| Login-fail | **SAMEORIGIN** | 未设置 | 未声明 SameSite |
| Login-ok | **SAMEORIGIN** | 未设置 | 未声明 SameSite |
| todolist1 | **SAMEORIGIN** | 未设置 | — |
| 消息中心 | **SAMEORIGIN** | 未设置 | — |

**结论**：OA 不能在 EternalAI 页面内以 iframe 打开，两个独立阻断各自成立：

1. `X-Frame-Options: SAMEORIGIN` 是全站设置；EternalAI 与 OA 不同源，浏览器直接拒绝渲染 iframe；
2. 即便前者放开，样本中的 OA `Set-Cookie` 未声明 `SameSite`，Chrome 默认按 `Lax` 处理，跨站 iframe 内不携带 Cookie，用户在 iframe 中是未登录态。

因此，「页面内嵌」对 OA 是**排除项**，不是「可能不行」。反向代理剥除 `X-Frame-Options` 会主动绕过点击劫持防护并破坏既有 CSRF 假设，不采用；OA 固定走**新窗口打开并保留来源引用**，承接 2026-08-27「前端信息架构与终态导航」已定的「外部系统工作区不占导航、OA 走新窗口」。若 OA 运维未来同时调整 XFO 与 Cookie 属性，须作为政策与运维变更重新实测，不在本决定中预设。

**适用范围**：本结论只基于 2026-08 的四份 OA HAR 样本，只对 OA 当前版本成立，不外推为「所有外部系统都不能内嵌」。接入第二个外部系统时必须分别实测。

### 二、「录制成功能」抓网络请求，不读 DOM

录制用户操作以生成新功能时，捕获的是**网络请求**，不是 DOM 操作：

1. 跨源 DOM 受同源策略限制，页面内容不可读；网络请求可在代理或本地 provider 层捕获；
2. DOM 操作序列会随页面改版或 class 名变化而失效，接口相对稳定；
3. 网络层才是契约层：DOM 上的几十个交互事件可归约为少量请求，参数化后直接形成 Capability。

这与既有 OA HAR 工作是**同一条技术路线**：`P2-OA-*` 系列已在把人工捕获的请求序列转为 Capability；录制功能只是把 HAR → Capability 的人工流程自动化，不是新方向。录制式自动化长期只作为发现和验证需求的入口；一旦取得正式接口，应升级为稳定的 Adapter / Capability / Workflow，只有确实没有接口的旧系统才长期保留浏览器操作型功能。

### 三、录制的安全边界

以下均为将来录制功能实现必须逐条落测试的红线：

| # | 边界 | 依据 |
|---|---|---|
| 1 | **不得**把完整 DOM、隐藏字段、Cookie 交给模型 | 页面上下文注册只允许声明式白名单字段 |
| 2 | 密码框、Token、Session、验证码、原始按键**一律不记录** | `AGENTS.md` 不可协商规则 4；`ARCHITECTURE.md` 不变量 5 |
| 3 | 只记录「填写申请日期」等**动作语义**，不记录用户当时填写的真实日期、姓名等个人数据 | 凭证与个人数据不得固化进功能定义 |
| 4 | **页面文字是不可信外部内容，不得当作 AI 系统指令** | prompt injection 防护；2026-08-18「卡片只做路由、不承载自由文本执行」同源边界 |
| 5 | 一次录制只证明**一条成功路径**，不能自动证明异常分支、权限、重试与幂等 | 录制产物只能是草稿 |
| 6 | 录制结果只能是**功能草稿**，不得直接发布或自动执行 | 2026-08-18 已定：`SkillCandidate` 只能由人主动登记，系统不得根据使用记录自动提出待审建议 |
| 7 | 页面版本或结构变化时**暂停该功能**，不得继续猜测点击 | 失败必须显性，不能静默降级 |

合规流程固定为两段式：用户主动点「录制为功能」后生成 `SkillDraft`（本人可用）；用户再次主动点「提交审核」后才进入 `SkillCandidate`。不得后台偷偷学习或自动发布。

### 四、录制前置空白

Local Worker 信任合同与浏览器扩展信任边界均尚未裁定，分别登记在 `PHASE2_PLAN.md` 欠债表。任何录制实现不得在前置空白存在时把本地抓包端点或浏览器扩展当作已定设计。

### 五、任务交办是既有插槽式模块边界的具体应用

本条是 2026-08-18「插槽式模块边界」在任务交办上的**具体应用**，不创建新的插槽模型。任务交办按稳定契约、静态注册表与 allowlist 独立开发并在构建或部署时装配，不采用运行时插件容器，也不默认拆成独立微服务、独立账号或独立数据库。

| 任务交办软件自己负责 | EternalAI 核心继续负责 |
|---|---|
| 任务描述与结构化表单 | 当前人员、组织范围与授权 |
| AI 生成草稿 | Work Object 的统一事实 |
| 接收对象解析、批量选择、去重交互 | 发布 / 改派 / 撤回的最终权限判定 |
| 回执、提醒、可见范围配置 | Policy / Gateway / Trace / Evidence |
| 发布预览与发布记录页 | 系统级幂等、审计、数据隔离 |
| 自己的草稿状态 | — |

**硬边界**：任务交办软件可以通过 Work Object Command Port 创建 Work Object，但不能建立第二套任务事实库，不能直接写 EternalAI 数据库，也不能绕过 Identity / Organization Scope / Policy / Idempotency / Trace / Evidence。

**顺序调整**：插槽只能依赖稳定合同。先冻结软件清单合同、Host Context 合同、Work Object 发布命令与回执、页面向 AI Dock 注册上下文合同，再让核心线与软件线并行：核心线实现 Work Object 双权威模型、部门授权范围与发布 Port；软件线用合同桩开发任务交办前后端、页面与业务规则，最后只做接入与合同测试。现有 `MODEL → SCOPE → DISPATCH → ATTACHMENT` 串行链若需拆成「核心发布合同」与「任务交办软件」两线，属于后续 GOV-SYNC 的 DAG 裁决，不由实现棒自行调整。

## 2026-08-28 — 裁决：插入 `P2-USER-ACTION-SEAM-001`，结构化 `UserAction` 先于 Renderer

**决定**：在 `P2-SDUI-RENDERER-001` 之前插入新棒 **`P2-USER-ACTION-SEAM-001`**（A 档）。串行顺序改为：

```
P2-USER-ACTION-SEAM-001 → P2-SDUI-RENDERER-001 → P2-LOW-RISK-WRITE-001 → P2-GOLDEN-002
```

**问题**：冻结蓝图的 SDUI 安全边界段逐字规定「前端不得直接执行业务动作；按钮点击只产生结构化 user_action；所有 user_action 必须回到 Runtime / Capability Gateway；所有用户点击、确认、拒绝、取消必须进入 Trace」。`UserAction` 在 `app/contracts/sdui/models.py` 有定义、经 `app/ports/response_envelope.py` 重导出、有形状合同测试，但**全仓没有生产使用点**：`app/api/v1/runtime.py::HandleRequest` 只有 `channel` / `session_id` / `message` / `client_capabilities`，`web/` 与生成 TS 中也没有 action 请求类型。GT-007 fixture 里的 `given.user_action` 是未被消费的元数据。

**为什么拆棒而不是扩 Renderer**：接线是后端纵切（API 判别式请求合同、Runtime 结构化 dispatch、fail-closed 分支、OpenAPI/Orval 重生成），Renderer 是前端呈现。压进一棒则任一面回炉即整棒回炉，且无法分离证明「按钮真的走了结构化路径」与「展示看起来对了」。拆棒后 SEAM 棒的交付物就是那条结构化路径本身。

**为什么不缩成只读展示棒**：`P2-SDUI-RENDERER-001` 是 `P2-LOW-RISK-WRITE-001` 的最后一项前置。缩范围后该前置解除不了，等于原地打转。**前置能力当前不可达（无 `_confirm` 后缀的生产能力），是要补前置的证据，不是删前置交付的证据。**

**`P2-USER-ACTION-SEAM-001` 的硬要求**：

1. 按钮提交结构化 `UserAction`，不生成也不解析自由文本；
2. 服务端按认证 Principal、session 与 `response_id` 查服务端 pending，**不信任卡片回传的可执行参数**，只执行服务端保存的 Capability 请求；
3. 校验不可变 action / request / binding manifest digest，并做**一次性原子 claim**；
4. missing / stale / mismatch / 重复点击**一律 fail-closed 返回明确失败，绝不跌回 Planner 或意图路由**；
5. 仍经 Runtime、Capability Gateway、Policy、Evaluator、Trace；所有点击、确认、拒绝、取消进入 Trace；
6. 既有自由文本确认入口保持可用，不得回归。

## 2026-08-28 — 裁决：`P2-USER-ACTION-SEAM-001` 的四项合同边界

结构化 `UserAction` 接线棒开棒前，四项公共合同 / 信任边界经雨爷拍板如下。第一项另经 Opus 5 与 codex `gpt-5.6-sol`（max）两方独立复核，三方结论一致。

### 一、租户维度：本棒沿用现有 `default` 语义，不统一改造主体合同

**决定**：`handle_user_action` 接收完整 `Principal`，但**沿用现有 tenant 语义**；**不**把 `handle_user_message` 一并改为接收 `Principal`。

**关键事实（推翻了开棒前的初始判断）**：`app/infra/auth/oa.py` 构造用户身份时写的是 `PrincipalOrgContext()`——**空构造，且是 `app/` 生产代码内唯一的构造点**——取的是 `app/ports/auth.py::PrincipalOrgContext.tenant_id` 的默认值 `"default"`。**认证层同样没有真实租户来源**，没有任何生产代码从 OA、配置或部门表推导出过别的租户值。（**2026-08-28 更正**：初稿写「全仓仅此一处」不准确——测试中另有 11 处构造，其中 `tests/api/test_work_objects.py` 两处显式传 `tenant_id="tenant-1"`。这一更正**加强**而非削弱本裁决：管道确实能承载真实租户值，**只是生产链从未填充**，故「统一改造」依然只会搬运常量。）

因此「统一改造」的真实效果是把同一个写死的 `"default"` 从 `app/runtime/runtime.py::RuntimeImpl.handle_user_message` 搬到认证层的字段默认值，绕一圈再送回来：**行为零变化，隔离能力零提升**。其副作用反而危险——代码从此**看起来**已接通租户，后继棒可能据此认为隔离已具备而不再设防。**一个诚实的硬编码加一条登记在案的欠债，比一条看着通了其实没通的管道安全。**

**另一条硬阻塞**：`RuntimePort.handle_user_message` 的签名逐字写在已批准规范 `docs/blueprint/phase0_architecture_freeze_and_mvp_spec_v1_0_11.md` §8.6.8，并由 `tests/ports/test_runtime_port.py::test_handle_user_message_signature_matches_spec_8_6_8` 逐项断言。**新增方法是「加」（老签名不动、老测试照过），改老方法是「改」（直接偏离已批准规范）**，后者按 `AGENTS.md` 属 GOV-SYNC 裁决事项，不得由实现棒自行决定。

**范围收窄两处既往表述**：

1. 「今天隔离能力本来就是零」**说过头**。用户、会话、request digest 与 binding manifest 四层隔离均已存在；为零的**只是租户 / 组织这一维**。
2. 「今天实际上只有一个租户」是运营前提，仓库无法独立证明；本裁决把它作为前提使用，不作为已验证事实。

**B 的必备条件**：新路径**不得**因为「反正是 `default`」就把租户维度从授权引用中省掉。2026-08-18「卡片动作的授权边界」要的是**绑定结构**而非真值——照常写入并严格比对 `decided_tenant_id`（复用现有 HumanGate 记录即自动满足）；**省掉该维度才是违规**。

**欠债定性升级**：租户未启用**不是普通待办**，而是**启用第二个租户之前的硬前置**。若第二租户先上线而欠债未还，相同 `ai_user_id` 与 session 组合可能共用 pending 键——轻则互相顶掉待确认，重则旧的裸确认文本命中另一租户的 pending。欠债登记在**病根**（认证适配器无组织身份来源）而非症状（运行时那行硬编码），承担棒 `P2-TENANT-IDENTITY-001`。

### 二、Trace 合同：新增最小 `user_action` 事件

**决定**：批准为 `app/ports/trace.py::TraceEventType` 新增**一个**取值 `user_action`，用 attributes 的 phase（`inbound` / `outcome`）区分入站与结果。

**为什么必须新增**：冻结蓝图 §3.4.5 逐字要求「所有用户点击、确认、拒绝、取消必须进入 Trace」，而现有 20 值闭合枚举**没有任何取值能表达用户点击**。借用 `admin_action` 是语义污染（那是管理面动作）；用 `response_envelope_created` 表达入站更不对（入站必须先于任何判定与响应）。

**边界**：只加一个取值，不加第二个；同一改动内更新 `tests/ports/test_trace_port.py` 的逐值守卫期望；phase 与 outcome 走 attributes，不再扩枚举。

### 三、Action 响应合同：`data` 两层命名空间

**决定**：结构化动作的响应在 `ResponseEnvelope.data` 下使用两层形状：

```
data = {"action_outcome": <闭合枚举值>, "result": <能力结果或 null>}
```

**禁止与能力结果平铺**——否则成功分支的能力数据与 outcome 会互相覆盖。

闭合枚举 `UserActionOutcome` 须覆盖全部拒绝分支，**包含 stale 与版本绑定冲突**（这两条路径当前走 `RuntimeImpl._finish_version_binding_failure` 返回 `status="failed", data=None`，客户端分不出来），并配一条与 `ErrorCode` 同款的闭合守卫测试。

**不扩** `app/ports/capability_gateway.py::ErrorCode`：它是 Gateway 执行失败的语义，与动作受理无关，且有 `tests/ports/test_capability_gateway_port.py::test_error_code_literal_values_match_spec_8_6_3` 守卫（**2026-08-28 更正**：初稿写的 `test_error_code_literal_is_closed` 是不存在的符号名）。前端无权读管理面 Trace，也不应解析双语文案，故拒绝分类必须机器可判别。

### 四、本棒只承接 `confirm`

**决定**：`P2-USER-ACTION-SEAM-001` 正式**只承接当前可达的 `confirm`**，不扩 `UserAction` 形状。

`app/contracts/sdui/models.py::UserAction` 的 `action_type` 是 `Literal["confirm"]`、`confirmed` 是 `Literal[True]`，并有形状合同测试锁定——**reject / cancel 目前结构上无法构造**。蓝图虽逐字要求这两个动作也进 Trace，但在合同扩展前它们不可能发生。

**这是显式裁决，不是方案作者自行后置。** 受控动作合同的扩展由 `P2-USER-ACTION-REJECT-001` 承担。

**影响面**：`PHASE2_PLAN.md` 的 `P2-USER-ACTION-SEAM-001` DAG 行与欠债表；新增四个承担棒的 DAG 行；`app/ports/trace.py`、`app/ports/runtime.py` 的契约变更授权范围以本条为准。

## 2026-08-30 — 裁决：`CapabilitySpec.output_schema` 是规范化输出暨 `ResponseEnvelope` 外露合同

**决定**：本项目不新增与 `output_schema` 平行的 display allowlist。
`CapabilitySpec.output_schema` 同时约束能力在可信执行边界后的规范化业务输出，以及该结果允许进入
`ResponseEnvelope.data` 和安全自然语言 formatter 的最大外露形状。它不是上游原始响应 schema，
也不是内部执行结果、Trace、错误详情或 adapter 私有字段的全集。具名 formatter 可以只使用该合同的
子集；未声明字段不得进入 `data`、`message`、`fallback_text` 或完整 envelope。JSON Schema 默认的
`additionalProperties: true` 不构成外露授权；只有具名 `properties`，以及明确给出子 schema 的
`additionalProperties`，才构成结构授权。

**凭证边界**：任何递归 `properties` 名命中统一的 `_CREDENTIAL_MARKER`，该外露合同即无效，
projector 对根结果 fail-closed 为 `data=None`；仓库守卫同时覆盖生产 canonical schema、Golden
注册能力与标记为有效的测试 fake。schema-valued `additionalProperties` 接收的动态键仍须在运行时逐键
执行同一 marker 校验，命中键不得外露。`ResponseEnvelopeBuilder._sanitize_value` 的键名和内容匹配
继续作为独立的纵深防御，不得因 projector 存在而删除或绕过。

**已知边界**：静态合同不能判断“一个已批准、marker-free 的业务字段，其运行时值实际上是任意形态的
凭证”。能力作者和 adapter 必须先把上游结果规范化，禁止把 password、token、cookie、session id、
access token、refresh token 或其他凭证放入任何获准字段；值层 marker 清洗只是一道补充防线，
不是把凭证放入业务字段的授权。本裁决不授权 raw payload、内部错误、Trace、Cookie 或凭证进入响应。

**校验边界**：projector 是外露塑形，不是完整 JSON Schema 返回校验；它不执行 `required`、`const`、
`enum`、`format` 等业务有效性约束，也不负责把返回合同违规转换成执行失败、错误码和 Trace。
`PHASE2_PLAN.md` 中“Registry `output_schema` 未参与返回侧校验”欠债保持未结项，本棒只更新其 evidence。

**渲染边界**：获准进入 `ResponseEnvelope` 不等于获准渲染成 DOM、`href`、导航或 Action。

## 2026-08-30 — 裁定：组织目录不承担授权判定，权限由 OA 自身执行

   允许的 scheme 闭集是 `http:`、`https:`。`http:` 不是全局放行：只有白名单中显式以 `http:`
   登记且规范化 origin 完全相等的目标才通过。本项目 OA 现役为内网明文 HTTP，一刀切禁止

## 2026-08-30 — 裁决：Admin 审计读取面的对象级授权模型

**决定**：Admin 管理配置权与审计证据读取权拆分。`admin` 单独不能读取
`app/admin/registry.py::AdminRegistryService.list_tasks`、
`app/admin/registry.py::AdminRegistryService.list_task_events`、
`app/admin/registry.py::AdminRegistryService.list_bindings`、
`app/admin/registry.py::AdminRegistryService.list_traces`；另设独立只读审计角色。该角色只获得证据读取能力，
不得获得 Registry、Binding 或执行类变更能力。同一人员可同时持有两类角色，但角色组合不扩大对象范围。
可信同租户内允许跨用户读取；跨租户对象查询统一不可见，集合查询返回安全空集合。

Trace 不适用 2026-08-21「个人备忘的隐私边界，管理员不得读取他人备忘」中的 owner-only 口径。
个人备忘的内容用途本身即为私人，管理职责不产生读取正文或附件的必要性；冻结蓝图 §9.2 把 Trace 定义为审计与
调试用的操作摘要，排查失败链、复核受控执行或形成合规证据客观上可能需要查看另一用户的执行链。
但“存在合法跨用户用途”不等于“所有管理员天然有权读取”：管理配置权与大范围证据读取权是两类独立风险，
必须由不同角色与对象范围分别约束。

`app/api/v1/admin.py::_request_context` 必须把认证后的
`app/ports/auth.py::Principal.org_ctx` 原样传入 `app/admin/registry.py::AdminRequestContext`；
可信主体租户进入 `app/ports/policy_guard.py::ManagementPlanePolicyContext` 的类型化字段，不能由查询参数、
目标标识或自由文本环境标签补齐。组织与部门字段保真携带，但继续只作展示或审计元数据，不作为允许依据；
改变这一边界须另作 superseding 裁决。

最终判据是：无相应角色与仅有 `admin` 的主体在四个证据入口均于资源 Port 调用前 403；只读审计角色可读取
同一可信租户内另一用户的证据，但跨租户使用相同 trace、task 或 session 标识仍不可见；只读审计角色不能执行
管理变更。调用方提交的用户或资源标识只能收窄查询，不能决定授权 scope。

实施复核确认一项裁决原先未预见的阻塞事实：
`app/ports/auth.py::Principal.org_ctx` 只能证明调用者自己的租户；
`app/ports/task_store.py::TaskRecord` 只有 `task_id`、`session_id`、`ai_user_id`、`status`、`trace_id`、
`capability_id`、`error_code`，没有租户维度；仓库也不存在从目标对象标识解析到可信目标租户的服务端来源。
因此“同租户跨用户读取成功”与“跨租户同标识不可见”在归属列落地前不可能同时满足。
`P2-AUDIT-READ-AUTHZ-001` 首次开棒已命中停手判据并零改动停手；当前 BLOCKED 于“可信目标租户来源未定”，
恢复路径待雨爷裁定，不得写成已决或可开棒。

审计修复仍拆为两根严格串行 A 棒：

1. `P2-AUDIT-READ-AUTHZ-001`：角色与动作分离、认证组织上下文保真、主体租户进入 Policy、对象关联与统一
   不可见语义。它是单租户下也成立的现役安全必达修复，但受上述目标租户来源阻塞。
2. `P2-AUDIT-TRACE-SCOPE-001`：`app/ports/trace.py::TraceEvent`、
   `app/ports/trace.py::TracePersistedEvent`、`app/ports/trace.py::TraceQueryPort` 增加可信租户/用户归属合同；
   `app/infra/observability/postgresql_trace.py::PostgreSQLTraceWriter.record_event` 固化归属，
   `app/infra/observability/postgresql_trace.py::PostgreSQLTraceReader._list_events` 无条件按可信租户 scope 过滤；
   顶层凭证形状在构造或写入前 fail-closed，原始持久事件不得直接外露。该棒在单租户 P2 中仍属机会层，
   但与前棒共同成为 `P2-TENANT-IDENTITY-001` 完成及启用第二租户的硬前置。

`P2-AUDIT-TRACE-SCOPE-001` 需要两次相互独立的专项授权：第一次授权 Trace 表 schema 变更；第二次授权历史行
回填。两项授权目前均未取得，裁决“必须做”不构成执行授权。历史回填材料必须说明可信映射来源、可归属与不可归属
数量、`app/runtime/runtime.py::RuntimeImpl.handle_user_action` 产生的孤立动作 Trace 如何处理，以及回滚策略；
不得用统一默认值猜测租户或用户，不得删除无法归属行。未取得可信归属的历史行保持 Admin 不可见。

**理由**：Policy 决定“谁能做哪类读取”，service 决定“请求指向哪个受控对象”，reader 强制“任何查询都不跨
可信租户 scope”，三层职责不能互相替代。只做 service 关联覆盖不了没有 Task 记录的孤立动作 Trace；只做 reader
过滤不能替代角色与动作授权。先冻结授权模型、再落 Trace 归属，可避免用尚未裁定的数据库字段反向定义权限；
当前阻塞则说明目标对象归属必须先有可信服务端来源，不能用单租户默认值伪造正向证据。

**影响面**：`P2-AUDIT-READ-COVERAGE-001` 盘点任务以结论 C 收口，现役 DAG 由
`P2-AUDIT-READ-AUTHZ-001 → P2-AUDIT-TRACE-SCOPE-001 → P2-TENANT-IDENTITY-001`
承接；`P2-TENANT-IDENTITY-001` 的完成判据新增 Admin 四个读取面的跨租户反证。
`P2-AUDIT-READ-AUTHZ-001` 当前 BLOCKED，`P2-AUDIT-TRACE-SCOPE-001` 另受两项未授权红线阻塞；
本裁决不授权任何 DB schema 变更、真实数据回填、Golden fixture 或 `FROZEN_GT_IDS` 变更。

## 2026-08-31 — 事实确认：任务派发链整体前置于组织目录，DAG 补一条缺失边

**决定**：`P2-INTERNAL-WO-SCOPE-001` 的 `depends_on` 增加 `P2-OA-ORGANIZATION-DIRECTORY-001`，并标记 BLOCKED。

**问题**：2026-08-21「任务派发拆四棒」把 `P2-INTERNAL-WO-SCOPE-001` 的依赖只写成 `P2-INTERNAL-WO-MODEL-001`；2026-08-27「部门层级在授权中的作用」虽然在实现要求里写明「`P2-OA-ORGANIZATION-DIRECTORY-001` 必须固化部门父子关系与唯一主负责人」，但这条依赖**从未传播进现役 DAG**。2026-08-31 实际开棒后零改动停手，暴露了这条缺失边。

**实测事实**（开棒窗口报告，协调窗口逐条复核）：

- `app/ports/auth.py::PrincipalOrgContext` 只有单值 `tenant_id` / `org_id` / `department_id`，**没有部门父子树，也没有主负责人身份**。
- `alembic/versions/` 下 11 个 migration **不含任何组织部门表**，无父子关系、无负责人映射。
- `app/ports/work_object.py::WorkObjectRecord` 与 `WorkObjectStorePort` 只有 assignee 维度，没有 `owner_department_id`、部门可见范围或主负责人合同。
- `docs/adr/phase2/ADR-P2-OA-DIRECTORY-001-readonly-directory-contract.md` 明确记载 `managerid` 语义未定，**不得猜成部门主负责人**。

因此 2026-08-27 裁决要求的四项——递归部门子树与环检测、主负责人跨层查看与派发、同级/反向/非主负责人隔离、基于服务端可信来源的接线——**在组织结构数据落地前均无法实现**，且无法在不猜测组织结构的前提下绕过。

**为什么这样定**：原 DAG 行的边界描述「内部部门树授权不依赖 OA 授权模型」**本身没错**——本项目确实不采用 OA 的授权判定（身份权限透传）。但它被误读成「也不依赖 OA 的组织结构数据」。两者是不同的东西：**不依赖 OA 判谁有权，不等于不需要知道部门树长什么样。** 补边时保留原句并就地澄清，避免下一个人再踩同一处歧义。

**影响面**：任务派发四棒链整体前置于 `P2-OA-ORGANIZATION-DIRECTORY-001`，现役顺序为
`P2-OA-ORGANIZATION-DIRECTORY-001 → P2-INTERNAL-WO-SCOPE-001 → P2-INTERNAL-WO-DISPATCH-001 → P2-INTERNAL-WO-ATTACHMENT-001`；
其中 DISPATCH 另需 `P2-PAGE-CONTEXT-CONTRACT-001`，ATTACHMENT 另受「方案限额矛盾须先裁」阻塞。
`P2-OA-ORGANIZATION-DIRECTORY-001` 若需要本地组织镜像表，属 **DB schema 变更红线**，须单独取得雨爷授权；2026-08-31 的 Trace 授权**不覆盖**该表。

## 2026-08-31 — 事实确认：`managerid` 不可用于部门主负责人，部门级来源另在部门表

**决定**：`P2-INTERNAL-WO-SCOPE-001` 的「上级部门主负责人」**不得**从 `hrmresource.managerid` 取得。该关系的来源改为**部门表/部门表单上的负责人字段**，具体字段名须在实现前以现场数据核验。

**两条互相独立的证据**：

1. **字段语义（联网调研，证据强度：官方文档）**：泛微云商店公开的 E9 后端 API 文档把 `managerid` 对应表单项标为「**直接上级**」，浏览对象是**人员**；E8 接口培训手册与维护手册镜像提供跨版本旁证。
   标准产品语义下 `managerid` 描述的是**每名人员自己的汇报对象**，不是「该人员所属部门的唯一主负责人」。
   某客户库中同一部门人员恰好大量指向同一人，只是**数据分布**，不会把字段合同改成部门属性。
2. **现场数据（雨爷 2026-08-31 实查）**：该字段在本项目现场部署中**所有人的值都是 `0`**，即**根本未启用**，不携带任何信息。

两条结论一致且互相加强：即便语义是「直接上级」，现场也取不到值；因此**无论如何都不能用它推导部门主负责人**。

**部门主负责人的真实来源**：官方 E9 API 的「获取部门表单」「查看部门信息」返回中，**部门表单上存在人员浏览字段**。社区数据字典整理出的 `hrmdepartment` 候选字段包括 `zzjgbmfzr`（组织架构部门负责人）、`zzjgbmfgld`（组织架构部门分管领导）、`jzglbmfzr` / `jzglbmfgld`（矩阵管理）、`bmfzr` / `bmfgld`；部分部署另有 `hrmdepartmentdefined.bmfzr`。

**这些字段名不是合同**：来源是社区数据字典而非泛微官网 schema 文档，且随 E8 / E9 / E10、数据库类型、KB 版本与二次开发而不同。**须以现场数据核验后才能固化**，核验前不得写进任何实现。

**为什么这样定**：`docs/adr/phase2/ADR-P2-OA-DIRECTORY-001-readonly-directory-contract.md` 原本把 `managerid` 列为「实现时仍须验证」的两点之一，判据是「不得创建猜测式映射」。本条以官方文档 + 现场数据双证据结束该项验证——**结论是该字段不可用**，而非语义待定。「已验证不可用」优于「语义未定」：后者会引诱后来者再去试。

**影响面**：

- `P2-OA-ORGANIZATION-DIRECTORY-001` 不建主负责人列、不建空位留位——空列会引诱后续用全 `0` 的 `managerid` 填入，形成静默错误的授权模型。
- `P2-INTERNAL-WO-SCOPE-001` 的「上级主负责人跨层查看与派发」（2026-08-27 裁决）**在现役采集面内无数据来源**，仍 BLOCKED。解除它需要先扩展 OA 只读采集面到**部门表单/部门信息端点**，并以现场数据确认该部署实际使用哪个负责人字段。
- ADR 中 `managerid` 那条「实现时仍须验证」**已完成验证**，结论为不可用；ADR 的 fail-closed 边界不变。
- 2026-08-27 裁决本身**不因此失效**——它规定的是授权规则，不是数据来源；若现场部门表也没有负责人数据，则该规则需另行重议，届时由 GOV-SYNC 裁定。

## 2026-08-31 — 事实确认：共享测试库未被污染，两个偶发失败是本机 Windows 环境缺陷

**决定**：**不重置测试库**。雨爷已授权重置，但重置前的取证证明重置无效且会销毁证据，故不执行。

**背景**：多根并行棒各自在共享测试库（`127.0.0.1:15432` 的 `eternalai_test`）跑过 alembic 往返后，`phase0/main` 上出现偶发失败，初判为状态污染。取证推翻该判断。

### 一、确实发生过一次真污染，已修复

`alembic_version` 曾停在 `20260831_120000`——该版本只存在于 `P2-OA-ORGANIZATION-DIRECTORY-001` 分支，`phase0/main` 无法解析，导致 `tests/db/` 五个用例报 `CommandError: Can't locate revision`。协调窗口 `downgrade` 到 `20260827_180000` 后恢复。

**这是并行棒共用一个测试库跑 migration 的结构性风险**，与下面两条无关。

### 二、`test_existing_human_gate_decision_maps_to_already_claimed`：测试替身保真度缺陷

`app/infra/human_gate/in_memory.py::InMemoryHumanGate.record_decision` 用**对象相等**判幂等：`existing == decision` 时静默返回旧对象，只有不相等才抛 `HumanGateConflictError`。

而 `app/runtime/runtime.py::RuntimeImpl._resume_pending_workflow` **只有收到 `HumanGateConflictError` 才**转成 already-claimed；幂等返回时会继续 resume，最终返回 `accepted`。

两条 decision 除 `decided_at` 外字段本就全同。本机实测**相邻 `datetime.now(UTC)` 采样 99,894/100,000 对相等**，故两次调用极大概率落在同一时间刻度、对象完全相等，冲突分支不触发。

**生产实现没有此缺陷**：`app/infra/human_gate/postgresql.py::PostgreSQLHumanGate.record_decision` 的 UPDATE 带 `AND decision IS NULL` 谓词，第二次认领匹配 0 行，必然走冲突分支。**认领一次性在生产端由 SQL 谓词强制。**

**因此这是 fake 比生产宽松**——该测试永远抓不到认领一次性的回归。属门禁覆盖性缺陷，不是生产安全漏洞。

### 三、`test_existing_oa_session_survives_upgrade_and_remains_loadable`：Proactor 事件循环不兼容

失败发生在**建立 psycopg async 连接时**，早于任何 SQL。本机默认事件循环实测为 `ProactorEventLoop`，psycopg async 不支持它，须用 Selector loop。

`app/infra/auth/postgresql.py::PostgreSQLCredentialStore.load` 的宽泛 `except Exception` 把驱动层 `InterfaceError` 统一包装成 `CredentialStoreError("OA session credential cannot be loaded")`，**掩盖了真实根因**——这是排查困难的直接原因。

排除了另外两种可能：不是行缺失（`load` 对无行返回 `None` 而非抛错），也不是解密失败（失败在连接建立前，decoder 未执行）。

`P2-OA-ORGANIZATION-DIRECTORY-001` 已在自己的测试里按仓库既有体例切到 Selector loop 绕过；**该绕法尚未推广到既有测试**。

### 四、为什么记这一条

雨爷在授权重置的同时追问「是否需要先检查」。**该追问直接避免了一次错误操作**：两个失败都与数据库状态无关，重置不会修好它们，却会永久销毁判定所需的证据——重置后两者都可能因偶发而变绿，从而被误记为「污染已清除」。

**结论：可重置 ≠ 该重置。授权是必要条件，不是充分理由。**

**影响面**：三项登记为欠债，均不阻塞现役棒——(1) `InMemoryHumanGate` 幂等语义与生产 SQL 谓词不一致；(2) `PostgreSQLCredentialStore.load` 的宽泛 `except` 掩盖根因；(3) 并行棒共用测试库跑 migration 会互相破坏 `alembic_version`。今夜已合并各棒的全量验证在污染发生**之前**执行，结论不受影响；协调窗口将在库恢复后于 `phase0/main` 重跑一次全量实证。
