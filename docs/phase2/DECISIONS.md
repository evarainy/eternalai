## 2026-07-24 — P2-AUTH-001 `cryptography` runtime dependency

`2026-07-24` 雨爷批准 `P2-AUTH-001` 新增运行时依赖 `cryptography`（OA 登录 RSA PKCS#1 v1.5 必需；`httpx` 已在，无新增 HTTP 依赖）。经 Claude 停点上报、雨爷显式批准。

## 2026-07-27 — P2-PILOT-FOUNDATION-001 `uvicorn` runtime dependency

`2026-07-27` 雨爷批准 `P2-PILOT-FOUNDATION-001` 新增运行时依赖 `uvicorn`，范围仅限 ASGI server 进程启动，不含部署编排。依赖白名单登记于 `docs/dev/dependency_policy.md` 的 Dependency Allowlist。

## 2026-08-03 — 决定一：写操作凭证与问责

写操作使用用户自己的 OA 凭证执行，OA 审批记录上是用户本人；每次写操作必须人工确认，AI 拟好、用户点确认才执行，确认动作本身留痕；与 `P2-CONFIRM-RESUME-001` 方向一致。

## 2026-08-03 — 决定二：数据库访问边界

数据库不算“目标系统”：不进外部系统名册、不做 IdentityMapping、不加 `db` 枚举值，因此不需要 schema 变更；但 AI 对数据库的每次访问必须在 Trace 里可查。

## 2026-08-03 / 2026-08-12 修订 — 决定三：企业级密钥

企业级密钥的责任人为运维；纯内网不设定期轮换；通过配置文件手工更新，不建设运行时管理页面。

## 2026-08-03 — 决定四：Golden 策略（逐字）

负向、边界和安全拒绝用例的题面、预期、禁止项、分类及判卷契约冻结，修改需雨爷明确批准。所有既有正向题面同样不可原地改写，只能新增后继题并在题外生命周期清单中停止旧题运行。判卷契约或运行选择规则变更时，必须按同一版本包全量回放并明确披露影响。每修复一个真实缺陷，必须新增一条能在未修代码上失败、修复后通过、且走原缺陷路径的永久回归证据；缺陷属于 Golden Runtime 观察边界时才新增 Golden Task，否则放在最小且忠实的单元/集成/API/浏览器层。

## 2026-08-17 — 蓝图原则修订：企业控制内核自有，通用执行内核复用

**决定**：蓝图 L2435「任何第三方框架都不能替代 Agent Runtime」修订为「企业控制内核（Gateway / Policy / Identity / Secret / Trace / Evidence）必须自有；通用执行内核（agent loop、上下文工程、持久 checkpoint、沙箱、子 Agent）优先复用成熟组件并保持可替换」；蓝图是冻结文件，落地方式是发 ADR 覆盖 L2435 / L2613，不编辑蓝图本体，具体框架选型仍未定。

**为什么**：实盘核对过——我们已建成的那些层第三方框架都不提供，而框架真正强的那些层我们完全空白，两边几乎不重叠，所以问题从来不是「要不要换掉自研」，而是「要不要补一层从没建过的」；同时 2026 年候选框架换代极快（一次一手核对里，三天内五个候选有三个变了版本语义），把执行底座冻进架构最深一层，等于把最大的不确定性锁死。

**影响面**：所有涉及多轮循环、缺参追问、规划、上下文工程、持久 checkpoint、子 Agent / 沙箱的后续任务；`AgentOrchestrationPort` / `WorkflowEnginePort` 接缝棒（欠债已登记在 `PHASE2_PLAN.md`）；此后任何「要不要引入某框架」的讨论以本条为起点，不再重开「自研 vs 复用」的原则辩论，只辩选型与时机。

## 2026-08-17 — 蓝图优化的落地顺序（四步走）

**决定**：按 `修文档漂移 → 内网真实 smoke → 修工具描述（能力模型可见面收紧）→ 留孔 + 装现成组件` 四步推进；前两步已完成（`P2-GOV-SYNC-011`；2026-08-13 内网 `smoke.ps1 verify` 全绿），当前落在第三步；「留孔」指补 `AgentOrchestrationPort` / `WorkflowEnginePort` 生产接缝，蓝图 L2373 / L2402 / L2403 早已写下这两个名字，只是代码里从未落地。

**为什么**：装第三方执行内核之前必须先有接缝，否则框架类型会长进业务代码——框架下次改 API 时改的是业务逻辑，想换第二家的成本比第一次更高；第三步是第四步的前置，两件必须按序，不能对调。

**影响面**：DAG 排序权归 GOV-SYNC，实现棒不得自行挑后继——本条即是已裁定的顺序，可直接机械传播；「装现成组件」不早于第三步收口，任何提前引入框架的提案先回到本条；补接缝本身是把蓝图欠的账补上，不是新增架构，因此不构成新的架构停点。

## 2026-08-17 — DeepSeek Harness：不引入运行时插件容器

**决定**：不采纳 DeepSeek Harness / Cordis 式的运行时插件容器（动态加载第三方代码、HMR 热插拔、同进程无隔离、显式宣称「没有 privileged core」）；其能力契约层与我们 `app/ports/` 属同构设计，不需要为它重构；可借鉴的只有两条——`Model-visible means logged`（进入模型请求的一切必须能从持久日志完整重建）与「能力的模型可见面只走单一 allowlist 投影」。

**为什么**：「没有 privileged core」与不可协商不变量「任何执行必须经 Gateway → Policy → Adapter → Evaluator → Trace 且不可绕过」正面冲突；运行时加载第三方代码会让制品不可复现、供应链审查失效；其 `inject` 的真实语义只是「等该服务就绪再加载」，不是权限模型；其可短路的 `waterfall` 事件链若承载强制通路，任一监听器不调用 `next()` 就能把 Policy / Evaluator / Trace 全绕过。

**影响面**：其他窗口不必重开「是否插件化」的调研；第四步「装现成组件」的候选范围排除运行时插件容器类方案；可借鉴的第二条与第三步「修工具描述」是同一个面（见 `docs/adr/phase2/ADR-P2-CAPABILITY-INJECTION-001-planner-contract-narrowing.md` 与 `PHASE2_PLAN.md` 能力注入欠债），并入该棒执行；第一条需先核实现有 Trace 是否已记录完整 LLM 输入，未核实前不排期。

## 2026-08-18 — 产品定位：AI 工作操作系统与三种工作表面

**决定**：EternalAI 不定义为聊天机器人、智能工作台、业务中台或企业 IM，而定义为部署在现有业务系统之上的 **AI 工作操作系统**。系统持续接收 IM、OA、文件、业务系统事件和人工输入，将其转化为可治理的工作对象，经 AI Runtime、Capability、Workflow 与 Skill 受控执行，再把同一工作状态投射到三种互补的工作表面：

- **通信空间 / IM（人与人）**：承载沟通、文件、通知，也是最重要的工作事件来源之一；
- **AI 共事界面（人与 AI）**：承载通用问题、开放任务、自然语言指令、连续协作与结果修订；
- **工作台（人与工作）**：承载责任、状态、时限、流程、阻塞、证据、确认和交接。

三者不是三个数据孤岛：IM 中的消息可以形成待办候选，AI 对话可以创建或继续处理工作，工作台结果可以返回原会话，工作对象可以追溯来源消息；身份、上下文引用、工作状态和审计记录必须贯通。原始消息仍以 IM 为权威来源，正式业务状态仍以 OA 等源系统为权威，EternalAI 的 Work Object 只作为跨系统工作编排状态的权威对象，不复制成第二套业务真相。

**覆盖关系**：本决定覆盖 `_scratch/ADR_前端体验架构_草案.md` 中「工作队列为主体」的产品级定位；工作队列仍是工作台的重要组成，但不再代表整个产品。该草案关于常驻 AI 入口、按结果寿命决定落位、复杂事项进入工作室、受控组件组合和 SDUI 与前端框架隔离的决定继续有效。

## 2026-08-18 — 聊天事件候选闸门：AI 止于候选，执行责任归人

**决定**：在「AI 读取聊天内容并识别潜在工作」这条路径中，AI 的自动权限永远止于 **Work Candidate / 待办候选**，固定链路为：

```text
聊天消息 / 引用消息
  → AI 提取事实、责任人、时限、来源和歧义
  → 生成待办候选卡片并推入工作台
  → 人工审阅、补充或驳回
  → 人工明确确认后转为正式 Work Object 并进入流程
  → 任何外部执行仍经 Gateway → Policy → Adapter → Evaluator → Trace
```

AI 不得仅凭聊天语义把候选升级为正式工作，不得把领导发言、群主身份、`@某人`、表情、已读状态或「好的/收到」等自由文本推定为执行授权。由聊天产生的候选升级、流程启动和任何外部写操作，都必须绑定一次明确的人机交互确认；Trace 至少记录确认人、确认时间、候选版本、来源消息引用、补充字段、确认结果和后续 Work Object。责任归属于作出确认的人，AI 负责建议、准备和留痕，不承担法定或管理责任。

一条消息可以产生多个候选，多条消息也可以汇聚为一个候选；不得强制建立 `message = task` 的一一映射。原始聊天内容不得直接灌入全局知识库或无边界 RAG，只能在显式触发和 Policy 允许的范围内读取当前消息、引用链及必要的有限上下文。

## 2026-08-18 — 聊天只做卡片路由，不承载自由文本执行

**决定**：人与人仍可在 IM 中自由交流，但 **AI 在聊天侧的工作交互只使用结构化卡片和受控按钮，不接受自由文本作为直接执行指令**。聊天借鉴审批卡片的交互方式，但只负责发现、通知和路由，不承载正式业务执行。

聊天卡片只允许执行以下类型的动作：

- 查看来源、查看依据或查看当前状态；
- 接受候选、驳回候选或标记稍后处理；
- 打开工作台中的结构化表单、事项工作室或确认页面；
- 对已经存在的工作对象进行签收、订阅或跳转。

卡片按钮不得直接调用业务 Adapter 或绕过工作台确认。候选卡片上的「进入办理」只表示接受候选并打开结构化页面；用户在工作台核对范围、字段、目标系统、风险和预期副作用后，再点击「确认执行 / 提交」才构成执行授权。「驳回候选」只改变候选状态，不等价于对源业务事项作正式驳回。

卡片动作使用稳定的 `action_id`、对象引用、版本号和幂等键，由 Surface Adapter 转换为统一 UserAction；不得把 Tool 名、任意 URL 或可执行参数直接塞进聊天消息。

## 2026-08-18 — 工作台向聊天反向推送：把注意力逻辑带回沟通现场

**决定**：工作台不仅接收聊天产生的候选，也应根据与「今日工作概览」相同的优先级逻辑，主动向适当的 IM 会话推送结构化提醒卡片，形成 `沟通 → 工作 → 执行 → 结果 → 沟通` 的闭环。典型触发包括即将超时、已经逾期、等待本人确认、AI 已准备完成、权限或数据受阻、需要交接和正式升级。

推送卡片只展示最小必要摘要、紧迫程度、责任归属和下一动作，并提供「去处理 / 查看详情」等路由按钮；不得在聊天中直接完成业务执行。推送必须引用唯一 Work Object，复用工作台的优先级、去重和状态计算，状态变化时更新原卡片而不是重复刷屏。

利用沟通环境的可见性形成责任提醒，但不得演变为模型自行决定的公开点名或排名：默认私发责任人；只有制度配置、原事项所在群或正式逐级升级规则允许时，才推送到群聊或负责人。接收范围、升级路径、频率限制、静默/班次策略、已读签收和每次推送都必须可配置、可审计。

## 2026-08-18 — Ant Design 6 卡片复用与多 Surface 渲染

**决定**：Web 阶段以 Ant Design 6 作为统一组件底座，同一份工作卡片语义与状态在 IM、工作台和事项工作室中复用，但按 Surface 采用不同密度：聊天使用紧凑卡片，工作台使用摘要卡片，事项工作室使用完整详情。复用的是 **语义协议、状态、动作合同和 Ant Design 6 组件实现**，不是强迫所有界面显示完全相同的布局。

协议继续保持语言和框架中立：权威源位于自有 SDUI / Work Card Schema，Ant Design 6 只存在于 Web Renderer。JuggleIM 消息载荷只携带卡片协议版本、对象引用和允许的动作，由 EternalAI Web Renderer 渲染；不得让通信产品的数据结构反向成为工作对象或卡片协议的权威定义。这样既能在当前 Web 产品中复用 Ant Design 6 卡片，也保留未来原生客户端新增 Renderer 的空间。

## 2026-08-18 — 插槽式模块边界：可替换，但不引入无特权核心的插件容器

**决定**：产品模块采用插槽式组合，借鉴 DeepSeek Harness 在模块装配、替换和维护方面的思路，但不采纳其动态加载任意第三方代码、HMR 热插拔、同进程无隔离或「没有 privileged core」的运行时插件模型。当前阶段的插槽由稳定契约、静态注册表和 allowlist 控制，在构建或部署时装配，经审查后才能进入产品。

优先预留的插槽包括：

- Communication Event Source / Delivery / Admin Adapter；
- Work Projection、首页优先级与角色视图；
- Card Renderer 与 Surface Variant；
- AI 共事面板、事项工作室辅助面板；
- Skill / App 入口与受控动作目录。

插槽解决「模块可以替换、独立维护、按需装配」，不改变企业控制内核的唯一性。任何插槽模块都不得绕过 Identity、Policy、Gateway、Evaluator、Trace 和 Evidence，不得自行扩大消息读取范围、发明新动作或直接执行目标系统操作；契约测试、架构边界测试和负向权限测试必须随模块实现一并提供。

**与 2026-08-17 DeepSeek Harness 决定的关系**：上一决定继续有效；本条只是确认可以借鉴其插槽化和可替换性，不恢复已经否决的运行时插件容器。

## 2026-08-18 — 当前前端与通信技术路线

**决定**：当前按方案 A 推进：EternalAI 保持自有 Ant Design 6 Web 外壳，以 JuggleIM 作为首个通信内核验证对象，通过自有 Communication Adapter 接入；工作对象、身份、权限、Policy、卡片协议和执行链均归 EternalAI。现阶段只做 Web，不开发桌面或移动原生客户端，也不再进行无目的 IM 选型调研。

重新打开通信产品选型的触发条件仅限：JuggleIM 验证出现硬性缺口；进入正式客户端开发里程碑；出现跨单位联邦通信、高安全加密等新增要求；或届时市场出现明显更合适的新产品。冻结蓝图本体不直接修改；本组决定作为后继决定生效，并在下一版蓝图中吸收。任何早期文档若允许「聊天自由文本直接驱动 Tool」「AI 自动把候选升级为正式任务」「聊天卡片按钮直接执行目标系统操作」或把工作队列等同于整个产品，均以本组 2026-08-18 决定为准。

## 2026-08-18 — 卡片动作的授权边界：引用不传递权限

**决定**：任何 Surface（IM、工作台、AI 共事界面、事项工作室）上的卡片动作，**授权依据只能是服务端签发、绑定到 `(tenant, principal, work_object, card_version)` 的不透明引用**。转发、引用、复制、截图重放消息或链接**不传递操作权**；服务端对每一次动作重新解析该引用并按当前 Principal 与 Policy 重新授权，主体失配一律拒绝并留痕。明文业务 ID（`task_id`、`work_object_id` 等）可用于展示、关联和日志，**不得作为授权依据**。

**为什么**：卡片进入 IM 后暴露出 Web 内没有的攻击面——消息可被转发、引用、搜索和截图，「卡片出现在你的会话里」不等于「你有权执行它」。若授权只依赖稳定 `action_id` 加明文对象引用，甲把候选卡片转给乙、乙点「接受候选」即可越权。该风险不限于 IM：工作台与共事界面的卡片引用同样会被复制粘贴，因此本条对所有 Surface 生效。

**影响面**：卡片协议与 `UserAction` 合同、Surface Adapter、JuggleIM 消息载荷字段、Trace 的拒绝留痕、后续所有 Renderer 实现；与 2026-08-18「聊天只做卡片路由」中的 `action_id`/对象引用/版本号/幂等键为同一套字段，本条规定其中「对象引用」必须是不透明且绑定主体的。

## 2026-08-18 — 本地 capability provider 的边界澄清

**决定**：「现阶段只做 Web，不开发桌面或移动原生客户端」**不排除本地 capability provider**。该 provider 不带浏览器内核、不带 UI、不是原生客户端，只是装在终端上、经 `localhost` 被 Web 应用调用的瘦服务，用于浏览器做不到的能力：Office COM、扫描仪、Win32 老软件、后台长驻任务。它与通信内核选型互不影响，予以保留。

**为什么**：桌面壳被否是因为 Electron / Tauri 在 Win7 与麒麟上只能冻结在已 EOL 的浏览器内核（依据见 `_scratch/查证_桌面壳与FileSystemAccess_20260818.md`）；本地 provider 不含内核，不受该约束。若不写明，「不开发客户端」会被读成连本地 provider 也一并排除，导致上述四项能力无处落地。

**影响面**：Excel 与本地文件场景的能力上限、终端分发方式、`Local Capability Provider` 相关的插槽与接缝；Excel 报表主流程仍以纯 Web（File System Access）为默认路径，本地 provider 只承接浏览器确实做不到的部分。

## 2026-08-18 — 通信内核的当前定性：初步筛查，未定选型

**决定**：JuggleIM 目前只是**架构完善所做的初步筛查对象**，不构成已定选型。当前阶段先把 Web 做出来、把流程跑通；IM 相关工作排在 Web 与工作流基本成型之后，**届时重新做选型决定**。现在不为 JuggleIM 编写验证清单、不做 IM 选型调研、不将其写入任何实现棒的前置。

**为什么**：2026-08-18「当前前端与通信技术路线」中「以 JuggleIM 作为首个通信内核验证对象」易被读成既定选型；实际用意是为整体架构预留通信层位置，验证时机在后。提前投入验证或实现属超前工程。

**与同日「当前前端与通信技术路线」的关系**：本条**修订**该决定中「重新打开通信产品选型的触发条件仅限……」一句——那句预设 JuggleIM 已近似选定、非例外不重开；实际用意是初步筛查。修订后的表述为：**IM 选型在 Web 与工作流基本成型后无条件重新评估**，原列四项（验证出现硬性缺口、进入正式客户端里程碑、跨单位联邦通信或高安全加密等新增要求、市场出现明显更合适的新产品）降为**提前重启的触发条件**，不再是唯一开口。该决定的其余部分（自有 Ant Design 6 Web 外壳、通过自有 Communication Adapter 接入、工作对象与执行链归 EternalAI、现阶段只做 Web）继续有效。

**影响面**：IM 相关三条 2026-08-18 决定（候选闸门、卡片路由、反向推送）的**协议与责任边界继续有效**，它们约束的是「AI 与聊天如何交互」这一类问题，与具体通信产品无关；受影响的只是排期与选型，不是这些边界本身。

## 2026-08-18 — 部署目标平台确认：ARM 架构银河麒麟 V10

**决定**：内网终端操作系统确认为 **ARM 架构银河麒麟 V10**（雨爷 2026-08-18 确认）。原「麒麟是 ARM64 还是 LoongArch 未知」的待验项到此关闭，后续不再以架构未知为由保留分支方案。

## 2026-08-18 — DeepSeek Harness 评估结项：经验证不适合，不再重开

**决定**：DeepSeek Harness（含 Cordis 插件模型）**经验证不适合本项目，评估到此结项**。相关调研材料与内网副本可清理，本条即为永久记录；此后不再重开该候选，除非出现推翻下列任一理由的新证据。

**不适合的理由（逐条，均经查证而非推测）**：

1. **架构冲突**：它显式宣称「没有 privileged core」，与本项目不可协商的「任何执行必须经 Gateway → Policy → Adapter → Evaluator → Trace 且不可绕过」正面冲突。
2. **强制通路可被短路**：其 `waterfall` 事件链中任一监听器不调用 `next()` 即可把 Policy / Evaluator / Trace 全部绕过；若把强制通路架在这条链上，绕过是一行代码的事。
3. **`inject` 不是权限模型**：其真实语义只是「等该服务就绪再加载」，不承载任何隔离或授权语义，不能拿来当能力边界。
4. **供应链不可审查**：运行时动态加载第三方代码 + HMR 热插拔，导致制品不可复现、离线交付与供应链审查同时失效——这在内网无镜像、依赖必须整体拷入的部署条件下不可接受。
5. **平台不匹配**：其 Node 引擎要求为 `^22.19.0 || >=24.0.0`，而 Windows 7 的 Node 支持终止于 13.x（2020-06-01 EOL）；作为客户端底座在目标平台上直接不可用。
6. **无重构收益**：其能力契约层与本项目 `app/ports/` 属同构设计，改用它并不能省掉已建成的层，只是换一套等价抽象。

**保留可借鉴的两条**（与否决不矛盾，已并入其他棒）：`Model-visible means logged`——进入模型请求的一切必须能从持久日志完整重建；以及「能力的模型可见面只走单一 allowlist 投影」，并入能力注入面收紧棒（见 `docs/adr/phase2/ADR-P2-CAPABILITY-INJECTION-001-planner-contract-narrowing.md`）。模块装配与可替换性的思路已由 2026-08-18「插槽式模块边界」条独立承载，不依赖该框架。

**影响面**：2026-08-17「不引入运行时插件容器」条继续有效，本条是其结项记录与理由固化；`_scratch/` 下以 DeepSeek Harness 为骨架的架构说明书 v0.1 / v0.2 已停止修订并被 2026-08-18 决定组取代；四步走第四步「装现成组件」的候选范围排除运行时插件容器类方案。

## 2026-08-18 — 「候选」正名：`WorkCandidate` 与 `SkillCandidate` 不得简称

**决定**：仓库中**禁止单独使用「候选」/`Candidate` 指代具体对象**，必须写全称：

| 全称 | 指什么 | 状态机 | 出处 |
|---|---|---|---|
| `WorkCandidate` / 待办候选 | AI 从聊天、OA、文件或业务事件中提取出的**工作候选** | 提取 → 人工审阅/补充/驳回 → 人工明确确认 → 转正式 Work Object | 2026-08-18「聊天事件候选闸门」 |
| `SkillCandidate` / Skill 候选 | 可登记、审查、拒绝，且**不能自动发布或执行**的 Skill 提案 | 登记 → 审查 → 接受/拒绝 | `P2-SKILL-CANDIDATE-001` |

适用面：类名、字段名、表名、API 路径、枚举值、Trace 事件名、错误码、测试名、文档标题与正文一律用全称。已有的 `P2-SKILL-CANDIDATE-001` 这一 `task_id` 保持不变（task_id 是历史路标，不改写），但该棒产出的所有代码标识符与文档表述须用 `SkillCandidate`。

**为什么**：两者的状态机形状几乎一样（登记/提取 → 审查 → 接受或拒绝），但对象、责任人、权限面和风险等级完全不同——`WorkCandidate` 被误升级会导致未经授权的业务执行，`SkillCandidate` 被误发布会导致未审查的能力进入运行时。一旦代码里出现 `CandidateStore`、`candidate_id`、`approve_candidate` 这类名字，读代码的人无法判断动的是哪一种，而这恰好是最不该猜的地方。命名歧义在这两个对象上会直接变成安全缺陷。

**影响面**：`P2-SKILL-CANDIDATE-001` 开工前须按本条确定标识符；`WorkCandidate` 相关的协议、卡片类型与存储在 IM/工作台棒中按本条命名；后续如出现第三类候选，同样必须带限定词，不得复用裸「候选」。
