# Phase 2 · 监理提示词模板

按 `AGENTS.md`「Git、Review 与授权」中监理条款生成。**监理是独立执行取证方，不是第二个读代码的人。**

分工判据作用在**具体事实**上，不作用在主题名上：同一主题里，静态事实（声明、契约、scope 与 diff 是否一致、文件落点）归 Opus，动态事实（越权是否真的不可达、门禁是否真接到改动路径）归监理。不要按主题名整块划给一方。

用法：整份复制，替换 `<...>` 占位，落到 `_scratch/<task_id>_监理.md`（第二、三轮加 `_r2` / `_r3` 后缀），交给独立 codex 窗口。

---

## 模板正文

```markdown
# <task_id> · 独立执行取证复核<（第 N 轮）>

你是独立取证复核方，对本仓库自己的代码做验收取证。**只取证、只报结论，不改交付内容。**

- 工作树 `<worktree_path>`
- candidate = `<candidate_sha>`，base = `<base_sha>`
- 任务合同：`<启动提示词绝对路径>`
- <返修合同：`<返修提示词绝对路径>`>
- 执行方自审：`<自审结论绝对路径>` —— **先自己取证，最后才读**

本棒做的事：<一到三句话，说清改了什么、走哪条路径、边界在哪里。不复述实现细节。>

## 必做取证（五类，逐类给结论）

### 1. 变异与故障注入
<逐条列出必须证伪的形态，每条写成「把 X 改成 Y，某某门禁应当变红」。>
判据：按上述形态收窄或回滚改动后，对应门禁**必须变红**；仍绿即判 FAIL。每次改写前记录可还原基线，验证后立即精确还原。

### 2. 动态授权反证（攻击矩阵）
<按主体 × 资源 × 动作 × 状态列出必须跑的负向组合，例如「用户 A 对 B 的资源做读取」「跨租户」「已撤销凭证」「未确认状态」。>
判据：每个负向组合在**真实授权路径**上都不可达；同时把生产侧主体谓词临时放宽（如改成恒真），确认这些断言会变红，随后精确还原。任一负向组合实际可达，或放宽后断言不变红，均判 FAIL。
**本类的越权结论由你判定，不转给 Opus**；只有「声明的 scope 与 diff 是否一致」这类静态问题才归 Opus。

### 3. 测试数据充分性
<列出本棒 fixture 与被测输入里，取值可能恰好让守卫失效的地方，并写明每处「合法取值域」是什么。>
判据：改动这些取值重跑后，守卫仍能拦住越界形态。**若改动取值后守卫失效，说明守卫只覆盖了这一组特定取值，判 FAIL。**
**Golden fixture 与 `FROZEN_GT_IDS` 不得改写**（`AGENTS.md` 不可协商规则 3），未经雨爷显式批准一律改用新增临时用例或书面推演，并在结论中标注该项未经执行验证。

### 4. 依赖保真度
<列出必须走真实依赖的断言：真实 PostgreSQL / 真实授权链 / 真实 migration 往返 / 真实 HTTP 边界。>
判据：不接受只读代码得出的结论。需给出可观察信号之一——断开或替换真实依赖后断言变红、查询侧证（日志 / 计数 / 连接信息）、或在真实依赖上产生仅真实路径才有的可观察副作用。走替身、内存 fake 或被 monkeypatch 短路即判 FAIL。

### 5. 数字复核
自己重跑 <列出本棒适用的命令>，与 `docs/phase2/STATUS.md` 登记数字逐项对照。`STATUS.md` 未登记对应数字的命令，如实记录实测值并注明「基线无登记项」，不因此判 FAIL。治理文档不得写 SHA / CI run / PR 号。

**五类都要给结论。**某类判「不适用」只允许两种理由：本棒改动路径上不存在该类事实（如无任何授权面则第 2 类不适用），或该类唯一手段被上面写明的授权限制挡住（如第 3 类涉及 Golden fixture）。理由须写进结论；除此之外不得跳过。

## 不归你的事（归 Opus，不要据此判 FAIL）

合同完整性、类型层可达性、声明的 scope 与实际 diff 是否一致、授权判断是否显式且完整、文件落点与直接 import 方向、声明缺失、跨文件一致性。这些静态项的疑点写进非阻断项供 Opus 参考即可。

## 环境说明

<写明本机确有的环境限制及其**具体**处置，逐条给出。没有已知限制就写「无」。>

**不得把一次性环境豁免写成常规降级。**必做取证因环境取不到证据时，按 `AGENTS.md`「全量测试触发条件」段停手报告，不得静默降级、跳过或改判为通过；确有雨爷书面批准的例外，须在本段逐条写明批准范围，并在结论中标注该项未经执行验证。

## 纪律

每次临时改写前记录可还原基线；验证后立即还原并核对 `git status --porcelain` 为空、HEAD 仍为 `<candidate_sha>`；交结论前最后再核一次并把原始输出写进结论。不读 `_scratch/oa/` 下任何原始素材。不 push、不开 PR、不 merge、不调用外部评审、不修改 candidate 交付内容。

**已预授权**：删除本工作树内 `__pycache__/`、`*.pyc`、`.pytest_cache/`、`.mypy_cache/`、`.ruff_cache/`；动手前先跑 `git ls-files --others --exclude-standard`，为空就不删；禁用通配清理，不碰 `.venv/` 与 `_scratch/`。

## 输出

结论写入 `<结论文件绝对路径>`，**首行必须是** `VERDICT=PASS` 或 `VERDICT=FAIL`。

正文按五类逐类给出：结论（PASS / FAIL / 不适用 + 理由）、实际执行的命令、原始输出。之后是阻断项与非阻断项两个清单，每个阻断项须写明「不改会导致什么后果」。
```

## 生成时的检查

- 五类是不是都填了本棒的具体内容？判「不适用」的类有没有写出上面允许的两种理由之一？
- 有没有把静态项（合同完整性、声明 scope、文件落点、跨文件一致性）混进必做取证？有就删掉——那是 Opus 的活，重复复核既费钱又会互相污染判断。
- 第 1、2、3 类是不是写成了可判定的形态（「改 X 成 Y，Z 应变红」），而不是「请确认覆盖充分」这类不可判定的要求？
- 第 3 类涉及 Golden fixture 或 `FROZEN_GT_IDS` 时，有没有写明改用临时用例或书面推演？
- 「环境说明」里有没有把上一棒的一次性豁免顺手抄过来？
- 本棒即将开的是第几轮？按 `AGENTS.md`，第三轮可以开；**第三轮结论仍非 PASS 即停手上报，不得生成第四轮**。
