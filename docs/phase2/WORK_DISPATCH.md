# EternalAI 任务派发模块开发说明

本文件是任务派发模块本轮完整开发的唯一实施入口，基于既有 Work Object 实现、原《任务派发与统一待办完整方案》和雨爷 2026-10-18 的业务确认及最终执行指令整理。业务裁决来源见 [DECISIONS.md](DECISIONS.md) 同日条目；当前已合并能力仍以 [STATUS.md](STATUS.md) 为准。

目标是交付真实可办理的领导交办、部门安排、跨部门协作、个人自办和周期任务。以下明确区分已确认要求、代码现状和实施默认值。文档完成不代表代码、Review 或 E2E 已完成。

2026-10-22 计划评审修订：开发以开工时更新并核对的 `origin/phase0/main` 为起点，不从旧交接 ZIP 的源码或导出基线施工。模块集中、薄宿主适配的目标保留。同日雨爷已批准 Schema A（仅清单内代码编写，不执行数据库）、Q03 独立角色保留可见权和 Q05 计划生成日后 N 天的固定时刻；具体规则见下文。独立计划复核与有界 schema 授权清单由仓库外交接资料承载，批准不等于实现或 Review PASS。

## 1 本轮范围和执行顺序

### 1.1 范围

| 编号 | 必须交付的业务能力 | 关键边界 |
|---|---|---|
| B01 | 人员、部门及混合目标派发，个人自办和备忘提醒 | 领导交办优先，但不裁掉其他场景；人工直接创建内部 Work Object |
| B02 | 可信角色、可选目标和参与者可见范围 | 派发、办理、查看三轴分离，不因管理员或领导身份获得全部任务查看权 |
| B03 | 部门负责人分配、持续跟进、审核和对外回复 | 部门成员不能自行抢接部门任务；负责人分配给自己也须显式操作 |
| B04 | 各自独立办理和主协办协作 | 独立办理分别办结；协作由唯一主办汇总，不能一人提交就伪造全部协办完成 |
| B05 | 接收、反馈、结果提交、部门审核、可选派发人验收与退回补充 | 部门审核与派发人验收是两层责任，不能互相代替 |
| B06 | 派发人修改、撤回、延期、改派；部门内承办安排 | 非终态才可改变业务；改派撤销原承办身份的查看权，独立派发人/相关负责人身份仍按其权限可见，保留办理历史 |
| B07 | 正式办结后整体冻结，仅备注可编辑 | 前后端及所有写入口一致；备注不能改变业务字段、负责人、完成时间或流转状态 |
| B08 | 周期规则创建、修改、开启、关闭、操作历史和逐期历史 | 周一至周日任选；上一期未完成也照常生成下一期 |
| B09 | 任务资料和办理结果附件的上传、关联、授权下载 | 原方案要求保留；办结后不能新增、替换或移除任务附件 |
| B10 | 统一工作台、我发出的、部门待分配、待审核、待验收和历史查询 | 无权事项的正文、结果、附件、计数、搜索与页面上下文都不能泄露 |
| B11 | 站内到期提示、逾期标识及真实错误反馈 | 周期生成不等于提醒送达；复用工作台提示，不新增短信、邮件或 IM 通道 |
| B12 | 现有 OA 待办兼容和必要一致性 | OA 仍是外部快照权威；不借此改造 Runtime、身份系统或全仓架构 |

保留现有会话内草稿能力及其刷新失效提示。AI 一句话解析、服务端持久草稿、附件在线预览/正文提取/病毒扫描、通用评论社区、工作流设计器和外部通知不是本轮新增功能；原登记欠债不因此关闭。本轮不另造完整任务平台、通用插件框架、消息总线、事件溯源框架或第二套身份系统。

### 1.2 本轮专用流程

这是一轮任务的执行约束，不改写为全项目永久规则。它按最新明确指令覆盖此前与之冲突的派工、前置 plan 评审、自审/Monitor/静态评审顺序及本地全量测试套餐；非冲突的权限红线、依赖方向、隔离、错误真实性、Git 和 CI 保护仍有效。

1. **A 文档整理**：当前窗口只读代码、联网比较成熟方案、整理文档和交接；不写业务代码或测试脚本，不运行业务测试。
2. **B 完整静态开发**：新窗口 Astra High 主控（雨爷 2026-10-22 再次明确保留本任务特例，不修改项目/全局配置），先核实实际 checkout 并完整读取新 worktree 的 AGENTS.md，再按本文件完成全部可实施业务代码、前后端合同及装配。允许只读 Ruff、mypy、TypeScript `--noEmit` 静态检查及必要 OpenAPI/Orval 生成，限制输出在授权路径，不启动业务或执行测试；C 的只读边界不变。不新增或修改测试脚本、不运行单元/集成/E2E/全量测试，不搭建测试基础设施。不能以缺测试为由暂停编码，也不能用 TODO、Mock 或空成功代替实现。
3. **C 独立静态 Review**：完整候选交 Opus 5.5 全新独立会话，以不同厂商模型只读核对需求、真实代码和完整 diff；不运行代码、构建或测试，不写测试脚本。Codex 窗口只能作可选补充，不能替代该跨厂商 Review，开发窗口自查也不算。发现交回开发窗口最小修复；影响结论的修复须由独立评审方核对最终候选。本轮阶段顺序不豁免跨厂商要求。
4. **D 必要验证和真实 E2E**：全部静态代码完成、独立 Review 完成且确认问题修复后才进入。复用已有工具，执行与改动直接相关的最小检查和真实业务闭环；不追求覆盖率、不新增完整测试工程、不绕过既有 CI。环境缺失的流程标记未验收，禁止用 Mock 替代。

开发属于跨层状态机与权限变化，按 **A 档、高风险** 识别，但本轮不因该标记恢复已被最新指令替代的流程。普通问题自主解决，重大未决权限或红线只阻断对应动作，其余工作继续。不得自行合并主分支。

**数据口径变化**：最终指令“开发不使用 Mock 数据代替真实业务数据、验收不使用 Mock”覆盖此前“可先模拟部门”的讨论。可在没有现场数据时完成静态合同与代码，但不内置假组织/假角色、不在 API 失败时返回演示成功。真实目录来源和岗位映射未具备时，如实保留外部条件。

**专项授权**：本轮授权文档和后续业务开发，不自动替代 schema/迁移、真实数据写入、凭证、原始未脱敏采集件、系统配置、删除、发布部署等专项授权。原讨论稿对旧范围的授权陈述不作为新增 schema 或新现场动作的凭证。开发窗口先核实可追溯的具体授权；缺少时记录 §9 外部条件并继续其他工作。不得修改 `.env` 或读取原始 OA 素材补齐证据。

## 2 业务规则

### 2.1 派发与查看

| 可信身份 | 可以派给谁 | 不由身份自动获得的权利 |
|---|---|---|
| 单位领导、分管领导 | 所有部门和所有个人 | 未参与任务的查看权 |
| 部门负责人 | 所有部门（含本部门）和本部门人员 | 直接派给其他部门个人；其他部门内部办理记录 |
| 普通人员 | 仅本人 | 向他人或部门派发；查看同部门其他人的任务 |

角色与部门关系必须来自服务端可信组织事实，不从前端角色标签、显示名称或 `admin` 推断。沿用已获批的负责人 jobtitle 代码 `frozenset({"75", "380", "1405", "1701", "1999"})`；不能把“不可猜 ID”误写成禁止使用已确认名单。单位领导、分管领导的岗位集合各用显式代码 frozenset，未获名单时初值为空、拒绝授予领导权限；禁止从 env、配置或 DB 动态读取授权名单。可信目录 adapter 可替换，不等于授权名单可配置。旧监区/跨部门允许集合不再参与本轮新派发授权，但历史值或诊断引用不得被误当现役权限；对应精确守卫在阶段 D 按新合同调整。

派发给部门的任务，由部门负责人承担对外第一责任，分配前后均负责跟进、对内统筹和对外回复；任务不能因为已经分配到个人而从负责人管理视图消失。多名负责人不能取列表第一人或按名字排序决定；按 2026-10-22 已确认的 Q07，只有唯一可解析负责人才能派发，缺失或多人均在创建前拒绝，批量整体失败。

默认仅派发人、当前承办人和相关部门负责人可看相应任务。“相关部门”仅取本任务当前有效、`target_kind=department` 的办理关系中的 `target_department_id`；已被替换的关系不授予权限。根行 `owner_department_id` 只是归属信息，不是负责人可见权来源，不能因个人目标属于该部门而放行。领导直接派给个人、本人自办任务均不产生部门负责人可见权；相关人员若另有有效派发人/承办人身份，按该独立身份处理。协作方能看共同要求与共享结果，不默认获得其他部门内部反馈、审核意见及未共享附件。仅本人自办的备忘提醒按个人范围处理，不因同部门自动公开；这是沿用原方案的实施默认值，见 Q01。

改派提交成功后，撤销原承办身份带来的任务及历史查看权；若原承办人仍具有独立的派发人或相关部门负责人身份，按该身份的当前权限保留可见性（Q03 已批准）。没有其他有效身份则不可继续访问；历史事件不删除。所有详情、列表、搜索、计数、活动、备注、附件和 PageContext 消费均检查当前授权，不能依赖旧接单记录或缓存，也不能因保留根可见权而保留旧承办关系内部记录权限。

授权读模型扩展当前 `AuthorizedWorkObjectScope`：保留 tenant/ai_user/department，增加从已验证会话取得的可空 `principal_directory_user_id`、由新鲜目录计算的 `responsible_department_ids` 及目录版本/有效期证据。当前参与关系不缓存成客户端可传 ACL，而由 Store 在查询时匹配。一个共享 SQL 根可见性构造器负责 manual_dispatch 的 tenant + 发起人/当前直接承办/相关负责人判定；负责人分支须存在同 tenant、同 task、`superseded_at IS NULL AND target_kind='department'` 且 `target_department_id` 命中 scope 的办理关系，不用根 `owner_department_id` 或个人目标的所属部门代替。所有读入口先过它，关系内部记录还须经过同源的子资源可见性条件，不能因为能看根任务就放出其他部门内部内容。旧 manual 未物化关系时不从根归属部门补造负责人权限，仅按可验证的直接发起/承办身份兼容；后续若获准物化关系，才进入同一部门关系判定。

目录缺失/陈旧只清空负责人资格，保留可验证的当前直接参与和发起人可见性；没有可信 directory_user_id 时不能补猜。目录不可用等其他错误维持既有明确失败，不能都当陈旧降级。重放、计数、搜索、活动、备注、附件与周期实例查询复用同一来源；OA/legacy 非 manual 分支不改权。Q03 按仍有效的独立身份求可见权限并集，不因曾经承办而恢复旧关系授权。

### 2.2 独立办理与共同协作

- 独立办理沿用当前每个目标一个内部 Work Object，同批回执负责分组，不引入带独立生命周期的“派发单”。一人办结不影响同批其他人。
- 协作任务使用一个内部 Work Object 承载共同要求和最终结果，其下的主协办办理关系记录各方承接、反馈、部门审核及提交结果。办理关系不是第二套任务聚合；每个协作任务必须明确唯一主办。
- 部门目标先由负责人明确承办人，承办人提交结果后由负责人审核并正式对外提交。负责人可以退回补充，不能以“提交即完成”跳过这一步。
- 主办汇总协办对外提交的结果，再按任务的完成模式提交或申请验收。各方内部意见不因汇总自动公开；共享结果由明确的提交动作产生。
- 个人接收的普通任务不增加部门内部审批；需派发人验收时仍进入验收。一个人兼任多个正常职责的操作均留明示记录，不自动代点审核。

### 2.3 完成和业务变更

派发时必选 `submit_completes`（正式提交即完成）或 `confirm_required`（派发人确认后完成）。现有 `receipt_requirement` 是交付要求文本，不能用关键词代替完成模式。

正式提交的主体：个人任务是当前承办人；部门任务是审核后的部门负责人；协作任务是主办（主办为部门时由其负责人）。验收不通过退回办理并给出原因，不伪装成完成。

未办结任务由派发人修改要求、撤回、延期或改派。部门负责人可以在自身部门办理关系内分配/调整承办人，不能据此修改派发人的共同要求、责任部门或对外截止时间。具体命令职责必须分开，不能把“部门内分配”实现成无边界跨部门转派。

修改保留原要求及变更记录，现有办理意见不覆盖。提交待审核/待验收后发生实质内容变更或改派时，不可验收旧结果冒充新要求已完成；最小处理为使该次提交失效、回到办理并要求重新提交，见 Q04。延期只改变截止时间和对应提示，不重写历史。

### 2.4 办结冻结和备注例外

正式办结即整体冻结。保留原有查看权限下的标题、内容、派发对象、负责人、提交结果、审核验收、附件及历史。只有备注可编辑；不允许重开、重新派发原对象、改派、撤回、延期或修改其他业务字段。

`withdrawn` 不是完成：停止业务流转且不填办结时间。建议与 completed 共用业务冻结判断、保持当前参与者只读、备注沿用 Q02；该默认方案见 Q08，未获业务确认，不添加重开入口。

冻结作用于 Work Object 和其办理关系、结果、附件关联，不只作用于一个状态字段。独立办理同批已办结成员冻结；未办结成员仍可独立办理。协作任务正式办结后，其主协办办理内容同时冻结，不能借子记录入口继续改变任务。

复用现有命令事务，在写入前检查当前状态、角色和允许字段。一般修改接口、旧 `complete` 命令、批量入口、附件关联和后台作业都不得绕过同一个业务判断。备注请求只能携带备注字段，不接受夹带标题、状态或责任人；前端只读展示仍不能替代后端限制。

现有任务模块没有独立备注功能。最小方案是任务级纯文本备注，独立存储当前值和版本历史，明确与办理反馈、正式结果、不可变活动记录分离；不搭建评论线程。协作任务根备注属于共享内容，编辑处须提示可见范围；部门内部反馈/审核意见仍放在受限办理关系内，不混入共享备注，备注历史遵循相同共享范围。备注只更新自身修改人/时间和版本，使用自身 ETag；不修改根任务 version/updated_at/completed_at，不复用根生命周期事件的 result_version 唯一序列。写入仍锁根核对当前权限及相应规则，避免改派与备注并发绕权。备注权限的实施默认值见 Q02。

### 2.5 周期任务

周期规则是生成配置，每期生成普通内部 Work Object，不能复用上一期对象改日期。规则自身可修改、开启和关闭，不受某一期办结冻结影响；修改不能反写已生成任务。

- 选择周一至周日任意非空集合，全选即每天，单选即每周该日；按自然星期运行，不自动处理法定节假日或调休。
- 配置生成时刻、明确时区、开始日期及每期截止规则；页面显示时区，不隐式采用服务器本地时区。存储时间保持 UTC。Q05 已批准：截止时间取计划生成日在规则时区的日期加 N 个自然日，再取指定固定本地时刻；N 为非负整数，N=0 表示当天（如 17:30）。不采用实际生成时刻加时长；补发沿用计划日计算，可能生成时已经逾期。
- 任务模板包含普通派发所需字段、对象、独立/协作模式及完成模式，每期保存生成时的规则版本和内容。
- 上一期未完成或已逾期，下一期照常生成，各期互不覆盖、各有状态和历史。
- 关闭停止后续生成，已有任务继续办理；重新开启从下一次计划时刻生效，不补关闭期间的任务。修改仅对以后生成生效。
- 查看规则修改/启停记录和逐期历史，不能只展示最近一期；历史详情依当前任务权限，不能从周期列表恢复旧承办人访问权。
- 规则创建者负责规则编辑/启停，且每期派发仍须按其当前可信权限校验。权限或目录失效时显示生成受阻，不静默成功、不降级成管理员执行。
- 后台不复用登录凭证或伪造 Principal：规则保存创建时从已验证会话取得的 tenant、ai_user_id、directory_user_id，后台以持久主体引用在新鲜目录重判。缺失/歧义/不再具备派发权则当期受阻；不把创建时岗位权限永久烘入规则。账号停用/规则撤销与后台持续授权边界见 Q06，未有相应事实时不得声称实时撤权已验证。
- 同一期只生成一次：同一事务提交期次标识、普通派发结果、规则进度与活动；唯一约束以规则和计划发生时刻标识期次。规则修订号不能成为重复生成同一时刻的借口。

截止表达以 Q05 已批单一模式实现；服务开启期间停机漏期补齐、关闭期间不补仍为待确认默认值，不因本次截止表达批准而升级为已批业务决定。不引入自由 Cron 表达式、月末、节假日日历等未要求的扩展。

### 2.6 附件和提醒

沿用原方案的任务资料与完成证据用途，上传失败不能显示已上传、不能把缺失证据当作已提交。下载始终通过当前任务授权，不返回永久公开地址。办结前已关联文件办结后可按权限下载，不能通过重新关联、批量附件入口修改已冻结内容。

当前主干没有任务附件上传端点。本轮技术方案采用单文件原始二进制请求体、有界分块读取，沿用现有鉴权/CSRF 和统一传输，不新增 multipart 依赖或改依赖锁。文件与受限元数据存 PostgreSQL 独立附件表，引用/关联与任务写入在同一事务，列表不加载二进制；清单内代码编写已获 Schema A 授权，数据库执行未获授权，不是已完成能力。附件有自身版本，关联变更另检查根版本与冻结；不把文件内容写入根任务 JSON。缺少已发布任务上下文的派发前上传采用受当前身份约束的暂存引用，发布时原子关联。保留小型私有文件 Port，未来替换存储只换 adapter，不建设文件平台或自动清理作业。

原方案限额作为可调整默认值：PDF、DOCX、XLSX、PPTX、JPG、PNG；单文件 20 MiB、一次 10 个、任务总量 100 MiB。复用框架限长读取、检查类型/大小/实际格式及文件名路径安全，不执行或预览文件；格式检查不宣称等同病毒扫描。不新增自动删除作业以规避删除授权。

提醒沿用现有提前 7/3/1 天、逾期当天的选项，在站内工作台呈现到期和逾期提示；没有通知通道就明确称为站内提示，不宣称邮件、IM 或后台送达。周期实例生成、提醒提示、办结判定是三个不同动作。

## 4 最小模块设计和接口

### 4.1 责任边界

```text
现有 React 页面 → 生成客户端 → HTTP 路由
                                  ↓
                        任务派发应用服务
                      ↙           ↓           ↘
              纯业务规则     组织目录 Port     WorkObject Store Port
                                                ↓
                                      PostgreSQL 事务实现
周期触发器 → 同一应用服务；附件存储 → 小型 File Port
```

保留 `app/ports/` 不依赖 infra。角色、状态、冻结等纯判断集中在既有 `app/ports/work_object_scope.py`、`work_object_lifecycle.py` 或必要新 ports 文件，由 W0 定签名、W1 实现；Store 锁内复用这些中立判断，不能反向 import 应用包。星期计算可作为周期模块的纯计算。应用服务只编排现有身份、目录、Store 和附件接口。外部依赖只在真实替换点设 Port，不为每个命令建一个服务类。

建议落点是 `app/work_dispatch/`（应用编排与周期）、既有 `app/ports/work_object*.py`（合同/纯判断）、既有 PostgreSQL Store（事务）和同目录的独立周期/附件 Store 文件。不同时创建同名 work_dispatch.py；不引入第二个任务系统。原 WorkObjectService 的内部派发、选项与生命周期编排迁入新服务，新服务不依赖 CapabilityGatewayPort/RegistryPort；OA 同步、handling 和 capability 投影保留原处，混合列表只薄委托新的内部可见性。不改 PageContext/Capability ports 公共合同、runtime/config 或依赖锁。宿主共享修改只限 composition 装配及 application 生命周期/路由挂接，保留同期 AgentScope 改动。

### 4.2 模型和事务

- 任务继续使用内部 Work Object；独立模式延续逐目标创建；协作模式增加从属于该对象的办理关系，至少包含目标、主/协办、负责人/承办人引用、办理阶段和对外提交结果。
- 周期规则、规则版本及期次到 Work Object 的关联单独持久化；规则不充当任务正文的动态读取源，历史必须读当期快照。
- 备注、备注历史和附件独立成表且有自身版本；活动记录不可作为可编辑备注。附件关联带所属对象及内部/共享用途，不能只凭 blob ID 读取。根任务 completed 行保持原 updated_at/completed_at，备注不通过修改根行实现。
- schema 变更是完整范围的必要条件，不是“可能”：现有 manual_dispatch/lifecycle CHECK、事件 operation/transition 以及 Pydantic validator 都将旧四态和完成者/时间写死。2026-10-22 雨爷已批准 Schema A：允许按完整授权清单编写持久模型/校验/Store 与一个新 Alembic revision，含所列新表/列、CHECK、索引和外键；不执行数据库升级/降级、不写数据。W0 首先核对清单边界，新增范围须另批；Schema B 测试库执行仍未授权。只做本模块兼容扩展，不搬迁 OA 表、不自动回填真实组织角色、不改既有 OA 快照权威。旧 CHECK 用 legacy/new 判别式替换，不能整块放空。
- 沿用当前行锁、版本和幂等机制，授权、冻结检查、合法流转、业务写入、事件/回执放在同一事务。批量入口逐对象检查；不对包含已冻结对象的请求部分执行却报告整体成功。
- 当前 `create_internal_dispatch` 自己提交事务，不能先调用它再另外提交期次/规则进度。W1 提供只插入不 commit 的持久层 helper，W2 在独立周期 Store 文件拥有外层事务，一次提交期次唯一键、全部 Work Objects/办理关系、回执、活动和 next_due；普通派发仍由其 Store 拥有事务。session 不跨出 infra；失败整体回滚，不能拼装多个已提交操作。独立模式一期可关联多个 Work Objects。
- 旧内部任务缺新增配置时，依据既有语义处理为独立办理/提交即完成，已办结行保持办结；不能自动重开、重新派发或给历史结果补造审核。需要数据回填的部分先取得相应授权。

### 4.3 状态与操作合同

继续保留当前 `assigned`、`department_pending`、`in_progress`、`completed` 的含义。最小新增 `awaiting_department_review`、`awaiting_acceptance`、`withdrawn`；协作办理关系增加“已对外提交、待主办汇总”的阶段，不能把它误称为整个任务办结。前端、模型约束、响应校验和列表过滤须同步。

关系级命令携带稳定 `handling_relation_id`，包括对具体主/协办的分配、接单、反馈、提交和部门审核；根级修改/撤回/延期/验收命令不接受该字段，备注走独立资源。主办汇总提交与某一关系提交必须可判别，不能靠文本推测。业务命令沿用 Work Object 根版本：关系命令同事务检查根冻结、当前权限和根 If-Match，成功递增根版本；备注/附件资源各有自身版本，关联变更还须根授权与版本。W0 分别定义 ETag 所覆盖的响应，不让备注编辑修改已冻结根行。

| 操作 | 谁执行 | 结果 |
|---|---|---|
| `assign` | 目标部门负责人 | 待分配 → 指定本部门承办人；明确分配给自己亦可 |
| `accept` | 当前明确承办人 | 接单进入办理；沿用现有英文操作含义，不改作“验收” |
| `feedback` | 当前承办人 | 记录办理进度，不直接完成 |
| `submit` | 当前承办人/主办 | 部门内先待负责人审核；正式对外提交后按完成模式流转 |
| `department_review` | 相关部门负责人 | 通过则正式对外提交，退回则回办理；保留原因 |
| `confirm` | 派发人 | 待验收 → 正式办结 |
| `return` | 相应审核/验收人 | 回办理补充，原因必填 |
| `revise/withdraw/extend/reassign` | 派发人 | 非终态业务变更；改派原子更新办理关系和访问权 |
| `remark_edit` | 当前有备注编辑权的人 | 仅备注及其元数据变化，办结状态不动 |

旧 `complete` 写入口不能保留无条件直达办结的旁路：复用“正式提交并按完成模式推进”的同一判断，或显式拒绝不再适用的调用；不静默把需审核任务标成成功。普通自办可选择提交即完成，不额外要求自己再次验收。

### 4.4 对外接缝

下表是本轮开发基线，具体 DTO 在 W0 由单一负责人定稿并同步生成。不得一边并行编码一边由多个代理各自发明同名接口。

| 接口族 | 复用和最小扩展 | 约束 |
|---|---|---|
| `POST /api/v1/work-objects/dispatch` | 增加独立/协作模式、主办标识、完成模式、附件引用 | 保留现有幂等键、目标 ID 元组、真实目录解析与原子发布 |
| `GET /api/v1/work-objects/dispatch-options` | 返回当前可派对象/角色相关能力 | 无权对象不能靠前端筛除；自办返回本人能力 |
| 现有 list/detail/search | 增加参与关系、办理队列、冻结与可执行动作投影 | 保留 OA 分支；服务端授权过滤先于分页/计数；前端不自行推断权限 |
| `/{id}/lifecycle`、`/{id}/lifecycle/commands`、`/{id}/lifecycle/events` | 扩展上述命令、结果和活动可见性 | 沿用 `If-Match`、`Idempotency-Key`、错误码风格；结构化载荷不塞入自由文本 |
| `GET/PATCH /{id}/remarks` | 单一任务备注资源及编辑能力 | PATCH 仅允许备注文本；备注自身 If-Match，锁根核对当前对象授权 |
| 附件上传/关联/下载 | 最小私有上传引用与任务附件资源 | 服务端验证、作用域授权，冻结后只读，不提供通用公开 blob API |
| `/api/v1/work-object-series` | 创建、读取、修改、启停、历史和期次列表 | 不复用普通任务 PATCH 修改模板；规则变更仅未来生效 |
| 周期后台 `generate_due(now)` | 通过同一应用服务生成普通任务 | 生产触发器与期次事务分离；无 HTTP/React 依赖，无第二套派发权限 |

现有 JSON 传输不足以直接承载 ETag 响应头和附件字节流。由 W0/W5 单写 `web/src/api/mutator.ts` 的必要扩展或同目录薄适配，保留 CSRF、401 和身份 generation 处理；兼容既有生命周期取头路径，统一返回 JSON+必要响应头或二进制结果。UI 工作包只消费这些接口，不各自写裸 fetch 绕过身份处理。

若没有真实组织来源或所需权限，接口如实返回既有明确错误，不用空候选或默认成功掩盖。保持当前对象不存在/无权响应约定。未知结果只复用原请求键重试，不新造键自动补发；刷新后无法精确归因时保留明确提示，不借本轮建设通用恢复平台或关闭既有恢复欠债。

正文、备注、结果和附件内容仅在授权业务响应中出现，不进入诊断日志、Trace 或错误回显。现有鉴权、CSRF、身份代次、租户和凭证隔离直接复用；不为派发另建认证。

[Camunda 用户任务生命周期](https://docs.camunda.io/docs/apis-tools/frontend-development/task-applications/user-task-lifecycle/)可参考“指派与办理状态区分、应用负责授权”的设计经验；不引入其引擎、CQRS 或监听器体系。任务完成不等同于产品要求的“除备注外全部冻结”，冻结仍须按本项目的所有写入口落实。

## 6 开发顺序与并行工作包

开发主控先完成 W0，再分配不重叠的文件所有权。当前宿主可用并发为包括主控在内的 4 个槽位，所以最多同时 3 个子代理；新窗口按实际容量与用户最多 4 个子代理上限取较小值。不是强行开满。

| 工作包 | 输入和产出 | 文件所有权与禁止区域 | 依赖 |
|---|---|---|---|
| W0 合同和集成骨架 | 首先核对已批 Schema A 的完整清单；再定业务类型、授权 scope/SQL 读模型、DTO、接口/ETag、迁移切分和既有测试合同变化表 | 主控先写 ports 签名/DTO/OpenAPI/传输；冻结签名后显式把纯规则文件写权交 W1，避免两个包同时改；主控保留路由/装配/生成物所有权 | 首先完成；只编写已批代码，不执行数据库或开始测试 |
| W1 核心办理和持久化 | W0 → 派发/分配/主协办/审核验收/改撤延转/冻结/备注、共享授权谓词及事务插入 helper | 独占已交接的纯规则文件、`app/work_dispatch/service.py`、核心 Store 与获准单个新 migration；不改 W2 周期/附件 Store、前端和治理文件 | W0；schema 操作受专项授权 |
| W2 周期与附件适配 | W0 → 周期规则/逐期生成/历史、私有附件读写；调用不 commit helper，持有周期外层事务 | 独占 recurrence 应用模块及新增 recurrence/attachment Store 文件；不改 W1 主 Store；schema 需求交 W1 单写迁移 | W0 后可并行；清单内实现已获 A 授权，数据库执行仍未授权，集成依赖 W1 helper |
| W3 派发表单和周期界面 | W0 → 角色表面、独立/协作、验收、派发前资料暂存关联、周期配置/启停、完整规则操作历史与分页逐期列表 | 独占 `WorkDispatchPage.*`、`dispatchApi.ts`、`dispatchDraft.ts` 及新的周期 UI；提供历史组件和当期详情打开接缝，新页面 PageContext 遵守授权；不写生成文件、认证 store、AppShell、W4 文件 | W0 后可并行，无 Mock API |

通常首批 W1/W2/W3 并行，释放槽位后 W4 接入；高度耦合的 schema 与 Store 保持单写，不为增加代理数强拆。通用附件能力若经核对可复用则缩小 W2，不重复实现。

Schema A 已批准，后续开发窗口可完成清单内静态实现，不再因 A 未批阻塞 Store/迁移代码；缺 Schema B 仍禁止执行数据库，不能以静态候选完成声称真实验收。超清单部分须另行申请，继续独立可做部分。阶段 D 前保留测试代码不动，但 W0 必须列出旧四态、名单、服务路径守卫和迁移测试需更新的精确合同及新拒绝断言，不将预期旧合同失败当作自动放宽测试的许可。

W4 的撤权清退覆盖列表、搜索、详情、活动、备注、附件和现有 PageContext 注册；W3 对新增周期页面负责同等约束。当前会话身份没变不代表任务授权没变：遇到明确无权/不存在即撤销旧展示和上下文引用，不仅刷新列表。共享 hook、路由、附件组件和 props 由 W0 指定单一所有者，W5 挂接；不新建推送总线来承诺收回已经看见或下载的内容。

子代理默认 `gpt-6.1-sol` + `medium`；窄检索用 `low`；确有复杂数据库/跨模块工作用 `gpt-6-astra` + `medium`。真正复杂问题回交主控 `gpt-6-astra` + `high`。所有子代理禁止 `ultra/max/xhigh/extra high`、禁止自行升级、禁止嵌套子代理。

使用可显式指定模型/effort 的普通 worker/explorer，提供完整输入和精确边界，不使用会锁定更高 effort 的历史 `b-worker`、`b-self-reviewer` 等角色。可用独立 worktree/分支时隔离写入，全部从含本文件的同一基线起步，由主控集成；共享 checkout 时禁止多个代理改同一文件或切换分支。每包输出文件、合同、静态完成项、问题及候选 commit，不虚构测试结果。

[Codex 官方子代理说明](https://learn.chatgpt.com/docs/agent-configuration/subagents)确认可显式配置模型/effort，也指出自定义角色文件可覆盖这些值。本轮使用显式调用参数和禁止嵌套的调度约束，不宣称已设置平台级“最大 effort”硬限制；新窗口核对实际调用参数与返回信息，不能核验的部分如实记录，不改全局配置掩盖限制。

## 7 独立 Review 交接

W5 完成后生成仓库外 Review packet：需求文件版本（含 §11 Schema A 授权范围）、基线与候选 commit、完整原始 diff、新文件内容、逐项完成表、未决事项、范围与禁止路径。交 Opus 5.5 全新独立会话，不能 fork 已施工上下文充当独立性；Codex 评审只能作可选补充，不能代替跨厂商静态 Review。接口/分支信息不足时返回缺项，不假设实现存在。授权清单、实现候选及其差异须可由 Git 追溯，不能仅引用仓库外可变文件。

Review 检查：B01–B12 完整性；状态和字段接线；前后端冻结、备注白名单与批量/旧接口旁路；角色、部门、租户、改派撤权及协作内部记录；周期期次和快照；事务一致性；公共能力复用；模块可替换性；明显无依据的捕获/重试/降级/抽象；TODO、禁用按钮和假成功。

7:3 是业务投入为主的指导，不机械统计代码行。Review 应明确指出是否出现辅助设施挤占功能、单操作多层包装或重复校验；必要的权限、事务和冻结判断不能以精简为由删除。每条发现给出实际代码位置、需求依据和可发生的影响，不要求处理无业务依据的假想极端情况。

输出 PASS/需修复/BLOCKED 及严重度、文件、理由、最小修复建议；静态 PASS 不宣称 E2E 成功。修复后重新绑定最终候选；不借评审新增无关需求或全仓治理工作。

## 8 必要验证与真实业务验收

仅阶段 D 执行本节。先确认环境、实际账号角色、真实目录、授权测试数据及 schema 状态，再使用现有浏览器/HTTP/数据库日志链路。不得为验收读取未授权原始采集件、创建真实人员任务或执行生产数据操作。

| 场景 | 必须看到的真实结果 |
|---|---|
| E01 角色派发 | 两类领导向部门/个人成功；部门负责人向外部门成功、向外部门个人拒绝；普通人只能给自己派发。个人自办与领导直派个人不因 owner_department_id 向其部门负责人开放；有效部门关系才授予相应负责人可见权，列表/详情/搜索/计数/子资源一致 |
| E02 部门责任链 | 普通成员不能抢接；负责人分配后仍可跟进；承办提交 → 负责人审核 → 对外提交 |
| E03 独立与协作 | 独立成员分别办结；协作主办汇总，各部门内部意见不向其他协作方泄露 |
| E04 两种完成模式 | 提交即完成正确办结；需确认的提交后保持待验收；退回补充后可重新提交；部门审核不被跳过 |
| E05 变更与撤权 | 未办结改/撤/延/转有实际效果及历史；无其他有效身份的旧承办人原链接、搜索、活动和附件访问被拒绝；兼派发人/相关负责人的旧承办人仅保留该独立身份可见范围，不能读旧承办身份专属内容；新承办人正常接续 |
| E06 办结冻结 | 页面只读；真实请求修改标题/内容/对象/负责人/完成状态、撤回/转派/延期、附件关联及已有批量路径均拒绝且数据未变 |

| E08 周期任务 | 所选星期生成普通任务；上一期未完成也生成下一期；重复触发同一期不重复；截止按规则时区的计划日+N固定时刻，覆盖N=0、跨日与迟到补发不顺延；改规则不改历史；停用不生成、恢复按约定继续 |

| E10 一致性与兼容 | 重复提交不重复派发/流转；并发改派与旧承办提交只有合法结果；OA 快照不被内部命令改写，跨租户拒绝 |

周期验收使用真实运行的调度路径、时钟和持久化结果，不把直接调用生成函数一次称为“定时任务已验收”。需要跨时点的观察如实等候/记录；不能模拟时间或假目录冒充现场闭环。仅函数级检查可作为补充证据，并单独标注。

最小检查选择来自现有 [后端技能](../../.agents/skills/backend-task/SKILL.md) 和 [前端技能](../../.agents/skills/frontend-task/SKILL.md)：受影响类型/lint/build、API 生成一致性、最近的既有测试及必要负向场景；选中的组件测试仍逐文件独立进程。只有到了阶段 D 才允许为真实缺口增加少量回归脚本。不存在强制的新测试工程、覆盖率目标或本地全量套餐；既有 required checks 必须照常通过，不能删改绕过。不得用跳过、弱断言、空返回或反复重试换绿。

内部服务抽离不自动豁免 Golden：若实际改变其覆盖的终态、负向或公共语义，阶段 D 仍按实际影响执行；不修改冻结 fixture。固定测试库先确认无其他窗口使用并取得相应写入授权，迁移/回归与 runtime 窗口串行；不擅自换库、建库或改连接目标。新迁移默认一个 revision，只有尚未应用/发布的候选才可在核对主干后调整父版本；已应用历史不能随意改链。

每个 E 场景记录环境、候选版本、主体关系（脱敏）、实际操作/接口、可核对的前后状态、时间和最小日志引用；敏感正文、Cookie、令牌和人员数据不进报告。业务状态写入不一定等于页面成功，须核对前后端同一对象。失败先保留事实、查根因、最小修复；受影响事实补核，不无依据扩大验证。
